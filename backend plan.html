Chapter 01 / Foundations

The stack — from copper wire to your handler function.

A backend engineer who cannot draw the path of a single HTTP request from a user's keystroke to a database row and back will, eventually, hit a bug they cannot fix. Every framework, every cloud abstraction, every serverless platform is built on the same stack. The names change. The layers don't. Chapter one is the map; the rest of the manual zooms in.

```

The journey of a request

You type example.com and press Enter. Before any of your code runs, eight layers of machinery have already done their job. Walking through them — in order — is the best one-page summary of backend engineering that exists.

  1. DNS resolution. The browser asks a recursive resolver to translate example.com into an IP address. The resolver walks the DNS hierarchy — root, TLD, authoritative server — caching answers at each step. A misconfigured TTL here can keep a dead server in rotation for hours.
  2. TCP handshake. The browser opens a TCP socket to the IP, port 443. Three packets — SYN, SYN-ACK, ACK — establish a connection. One round-trip of latency you cannot avoid, only amortise.
  3. TLS handshake. Browser and server agree on a cipher suite, exchange certificates, derive a session key. TLS 1.3 does this in one round trip; TLS 1.2 took two. The session key encrypts everything that follows.
  4. HTTP request. The browser frames the request — method, path, headers, body — and writes the bytes into the TLS-wrapped socket. On HTTP/2 and HTTP/3 this is a multiplexed stream rather than a fresh connection.
  5. The load balancer. The IP usually points to a load balancer, not your server. The LB terminates TLS, picks a backend (round-robin, least-connections, consistent hash on a header), and proxies the request.
  6. The kernel socket. On the backend host, the kernel's TCP stack receives the packet, reassembles the stream, and hands the bytes to whatever process is accept()-ing on that port. The process is your application.
  7. The application server. Nginx, Envoy, Tomcat, Express, FastAPI, Go's net/http — something with an event loop or a thread pool reads the bytes, parses the HTTP frame, and dispatches to a handler.
  8. Your handler runs. Five lines of business logic. Possibly a database query, possibly a cache lookup, possibly a call to another service. The 5% of code that does the actual work the user wanted.

And then the journey reverses. The response goes back through the application, the kernel, the load balancer, the network, the TLS session, the TCP socket, and finally a decoded pixel on the user's screen. Every layer can fail. Every layer can be slow. The senior engineer's job is knowing which layer is the one to suspect, given the symptom.

What "backend" actually means

A backend is a long-running process that accepts requests over a network, does something stateful or computational, and returns responses. That definition is doing more work than it looks. Three properties make backend engineering distinct from any other software discipline:

  • Concurrency is the default. A backend handles thousands of requests per second from thousands of clients at the same time. Every line of code runs in a context where other lines are also running. Locks, races, deadlocks, and queueing are not edge cases — they are the substrate.
  • State outlives the request. The database is still there after your handler returns. So is the cache, the message queue, the user's session. Bugs become durable. A bad write made at 3 PM is still wrong at 3 AM.
  • Failures are partial. A single backend depends on dozens of other systems — databases, caches, message brokers, third-party APIs. Any one of them can be slow, broken, or lying. Anything can fail, and most things will, eventually.

The senior backend engineer is the one who has internalised those three facts. They write code that assumes concurrent callers, careful state mutations, and partial failure of every dependency. The junior engineer writes code that works in isolation; the senior engineer writes code that works at 3 AM during a partial network split.

The mental model: layers + the boundary

Every backend service has the same internal shape, regardless of language or framework. A request crosses three concentric rings:

  • The edge. Where untrusted input enters: HTTP handlers, message consumers, scheduled job triggers. Parsing, validation, authentication, rate limiting live here. The edge is where you enforce that everything past it is well-formed.
  • The domain. The business logic. Pure, ideally — given an input, produces an output, with side effects expressed as data, not statements. This is the only layer that should have your company's name in the code.
  • The infrastructure. Where you talk to the outside world a second time: the database, the cache, the queue, the third-party HTTP client. This is where most bugs come from, because this is where the assumptions of the domain layer meet reality.

The boundary between domain and infrastructure is the most important line in your codebase. It is the line that determines whether you can swap PostgreSQL for DynamoDB without rewriting business logic, whether you can test the domain without spinning up Docker, whether a flaky external API takes down your service or just returns a degraded response. Hexagonal architecture (Chapter 4) is the formal name for taking that boundary seriously.

What this manual will and won't teach you

It will teach you the shapes — the patterns that recur regardless of stack. The shape of a connection pool, the shape of a retry with backoff, the shape of an eventually-consistent read after a write. You will see those shapes in PostgreSQL and in Redis, in Kafka and in HTTP, in Kubernetes and in your application code.

It will not teach you any single language or framework. The Spring Boot and Java field manuals exist for that. This is the layer above: the layer that's still true after your framework hits 6.0 and reorganises everything.

Field practice
When something goes wrong in production, walk the stack from the user inward and from your application outward, meeting in the middle. Most engineers panic-jump to the layer they know best (usually the application). The systematic walk finds the answer faster because it doesn't skip layers — and 60% of the time the answer is in DNS, the load balancer, or the database, not your code.
```

Chapter 02 / Substrate

The operating system — every backend is a kernel-space tenant.

Your backend doesn't run on a CPU. It runs on top of an operating system that runs on a CPU. The OS owns the file descriptors, the schedulable threads, the network sockets, the page cache, the virtual memory map. Every "weird performance issue" that isn't a database problem is, almost without exception, a misunderstanding of how the OS works. You don't need to write a kernel module. You do need to know what a syscall costs, why epoll changed the web, and what happens when you run out of file descriptors.

```

Process, thread, and the cost of a context switch

A process is an isolated address space with its own memory, file descriptors, and at least one thread of execution. A thread is a schedulable unit of execution that shares its process's address space and resources with its siblings. The kernel scheduler decides which thread runs on which CPU core, and for how long, before switching to another. That switch — the context switch — costs somewhere between 1 and 10 microseconds, plus a much larger hidden cost: cache lines that were warm for the old thread are cold for the new one.

The implication: a server with 32 CPU cores running 32 threads serving 32 connections is fast. The same server running 32,000 threads serving 32,000 connections is slow, not because the threads are doing more work, but because the scheduler is. This is the C10K problem, named after the milestone of handling 10,000 simultaneous connections. The answer to C10K — and the reason every modern backend server looks the way it does — is event-driven I/O.

Blocking, non-blocking, and the event loop

A traditional Unix read looks like: n = read(fd, buf, 4096). If no data is available, the calling thread blocks — the kernel parks it until data arrives. One thread per connection means N parked threads waiting for N sockets, all of them costing kernel memory and scheduler bookkeeping.

The fix is to ask the kernel "tell me when any of these sockets has data" and use a single thread to dispatch to whichever socket is ready. The Unix API for this evolved through select (limited to ~1024 fds, O(n) scan), poll (no fd limit, still O(n)), and finally epoll on Linux and kqueue on BSD/macOS (O(1) notification of ready fds via a kernel-managed event list). On Windows, the equivalent is IOCP. On modern Linux, io_uring goes further: it's a true async-I/O interface that batches operations through shared ring buffers, reducing syscall overhead by an order of magnitude.

Every event-driven server you've heard of — Nginx, Node.js, Netty, Tokio, libuv, asyncio — is a single (or per-core) event loop sitting on top of epoll/kqueue/IOCP. The "magic" of being able to serve 100,000 connections from a 4-core machine is just the kernel doing the bookkeeping the scheduler can't.

File descriptors and the resource limits that bite

A file descriptor (fd) is a small integer the kernel gives you for every open file, socket, pipe, or device. They are not free: each fd consumes a slot in the process's per-process limit (ulimit -n) and the system-wide limit (/proc/sys/fs/file-max). The default per-process limit on most Linux systems is 1024. 1024. That's enough to die under any real load.

Symptoms of exhaustion: accept() returning EMFILE ("too many open files"), connections refused, log lines about "no free file descriptors." The fix is always two things: raise the limit (ulimit -n 65536, or LimitNOFILE in systemd, or the equivalent in your container runtime) and find the leak. The leak is usually an HTTP client that doesn't reuse connections, a database driver that doesn't pool, or a file handle never closed in an error path.

Memory: virtual, physical, and the page cache

Each process sees its own contiguous virtual address space. The kernel maps virtual pages (typically 4 KiB) onto physical RAM as needed. Memory you allocated and never touched doesn't consume physical RAM — only when you write to it does the kernel back the page. This is why a Java process showing 16 GiB of "committed" memory might only use 4 GiB of actual RAM.

The page cache is the kernel's most important optimisation for backends: every read from a regular file is cached in RAM, so the second read is essentially free. A database's hot working set lives in the page cache as much as in the database's own buffer pool. When the OS reports "used memory" near 100% but the system is responsive, it's not full — it's caching. The free memory column you want to watch is "available," not "free."

The OOM killer is the kernel's last-resort response when real memory runs out. It picks a process — usually the largest, sometimes the one running away — and kills it with SIGKILL. Your process gets no chance to clean up; the logs may not even flush. Production hosts must monitor for OOM kills (dmesg | grep -i oom, or oom_kill events in the kernel log). In containers, the same mechanism enforces the cgroup memory limit — exceed it and the container is killed.

Syscalls and their cost

A system call is a controlled transition from user mode to kernel mode: your code asks the kernel to read a file, send a packet, allocate memory. The transition itself costs tens to hundreds of nanoseconds (less now that the spectre/meltdown mitigations have stabilised). What's expensive is what the kernel does inside the syscall and what it does to your CPU cache.

Two practical implications. First: every read/write you make should be as large as possible. Writing 10,000 bytes one byte at a time is 10,000 syscalls; writing them all at once is one. Buffered I/O exists for this reason. Second: hot paths in a high-performance server batch syscalls. io_uring takes this to its logical conclusion — your app puts operations into a ring buffer, the kernel drains them in batches, and the syscall cost is amortised across hundreds of operations.
```

```
Field practice
Three OS commands every backend engineer should be fluent in: top / htop (CPU, memory, top processes), ss -tnp (open sockets and who owns them), strace -p <pid> (what syscalls a stuck process is making). On a sick host, those three reveal the answer 80% of the time. Add perf top and you'll cover most of the remaining 20%.
```

Chapter 03 / Networking

TCP, TLS, HTTP — the protocols every byte travels over.

Networking is the layer most backend engineers stop learning at "I know what an IP address is." It is also the layer that gives them the most production grief. You don't need to write a TCP stack. You do need to know why your service holds 60,000 sockets in TIME_WAIT, why HTTP/2 was a real upgrade, why head-of-line blocking still exists in HTTP/2 but not HTTP/3, and why DNS is somehow always to blame.

```

The TCP/IP stack, in just enough detail

Four layers, simplified:

  • Link (Ethernet, Wi-Fi): frames between physically adjacent machines.
  • Internet (IP): packets routed across networks by destination address. IPv4 is mostly exhausted; IPv6 is the future you'll still be migrating to in 2030.
  • Transport (TCP, UDP): TCP gives you an ordered, reliable byte stream with congestion control. UDP gives you unreliable datagrams and stays out of your way. QUIC, layered over UDP, gives you TCP's guarantees plus less head-of-line blocking and encrypted-by-default.
  • Application (HTTP, gRPC, SMTP, Redis protocol, …): your bytes have meaning.

TCP — the three-way handshake and what it costs

A TCP connection starts with a three-way handshake: SYN → SYN-ACK → ACK. That's one round-trip of latency before the first byte of your data can flow. On a same-datacenter call, that's a few hundred microseconds; across a continent, 30–60 milliseconds. Setting up a fresh TCP connection for every HTTP request — what HTTP/0.9 and unconfigured HTTP/1.0 do — is why keep-alive exists.

A connection ends with a four-way teardown: each side sends FIN and gets ACK. After the local side has acknowledged the remote's FIN, the socket goes into the TIME_WAIT state for two segment lifetimes (~2 minutes on Linux). This is not a bug; it exists to absorb stray packets from the just-closed connection. But if your service makes thousands of short-lived outbound connections per second, you'll accumulate TIME_WAITs faster than they expire, run out of ephemeral ports, and start refusing connections.

The fix is not to enable tcp_tw_recycle (deprecated, breaks NAT) and rarely tcp_tw_reuse (subtle, can corrupt connections through NAT). The fix is to reuse connections. HTTP clients in every modern language pool connections automatically — but only if you create the client once and reuse it, not once per request. This is one of the most common production bugs in backends written by people who don't know about it.

Congestion control: why the first byte is slow

TCP doesn't blast packets as fast as your NIC allows. It runs congestion control — a feedback algorithm (Reno, CUBIC, BBR) that probes the network for capacity and backs off when it sees loss. A fresh connection starts in slow start: a small congestion window (typically ~10 packets initial CWND on Linux), doubling each round-trip until loss or steady state. The implication: the first MB over a fresh connection is much slower than the second MB over the same connection. Long-lived connections — gRPC streams, database connections, HTTP/2 sessions — amortise this cost to nothing. Short-lived connections never escape slow-start.

UDP, QUIC, and the move past TCP

UDP is the no-guarantees alternative: send a datagram and hope. DNS, SNMP, VoIP, online games — anything that prefers losing a few packets to retransmitting stale ones — runs on UDP.

QUIC (the IETF transport protocol, originally from Google) is the interesting development of the last decade. It runs on top of UDP but provides TCP-like reliability, multiplexed streams, mandatory TLS 1.3 encryption, 0-RTT reconnection, and crucially — independent per-stream loss recovery (the missing piece in HTTP/2). HTTP/3 is "HTTP semantics over QUIC." It is now widely supported in browsers, CDNs, and major server runtimes; most public-facing services should enable it.

DNS — never as simple as it looks

DNS is a globally-distributed key-value lookup with caches at every layer: the OS resolver cache, the recursive resolver (your ISP, 8.8.8.8, 1.1.1.1), and the authoritative servers for each zone. Lookups are usually fast (the recursive resolver has cached the answer for you), but the failure modes are subtle:

  • TTL surprises. A TTL of 300s means "this answer can be cached for 5 minutes." Changing a DNS record propagates slowly — and not monotonically; some clients see the new answer before others. Lower the TTL before a planned change.
  • Stale resolver caches. JVM in particular caches DNS lookups forever by default (networkaddress.cache.ttl is -1 if a security manager is set). Many subtle outages trace back to a JVM that latched onto a now-dead IP at startup.
  • The 5-second hang. Most resolvers retry on timeout; the first timeout is typically 5 seconds. A flapping resolver translates into 5-second tail latencies on every request. Monitor DNS resolution time as a first-class metric.

TLS — the handshake and how to make it fast

TLS does two jobs: authenticate the server (and optionally client) via certificates, and encrypt the traffic. TLS 1.3 is the version you should be running — TLS 1.0, 1.1, and SSL 3 are deprecated and known-broken. The 1.3 handshake completes in one round-trip; 0-RTT mode can send application data in the first flight at some replay-risk cost.

Costs to know:

  • Certificate chain validation. The client verifies a chain of signatures back to a trusted root. Each cert may trigger an OCSP check (online certificate status protocol); without OCSP stapling on the server, the client makes an extra HTTP request to the CA before completing the handshake. Always enable OCSP stapling.
  • Session resumption. A second connection from the same client can reuse the previously negotiated keys via session tickets (RFC 5077) or session IDs. This skips most of the handshake. Worth configuring on load balancers and in your clients.
  • Cipher choice. AEAD ciphers (AES-GCM, ChaCha20-Poly1305) are mandatory in 1.3. Hardware AES acceleration (AES-NI) is universal on x86-64 and ARM server CPUs; ChaCha20 wins on devices without it (mobile clients).

HTTP semantics — what the request actually means

An HTTP message has four parts: request line (method + path + version), headers, blank line, body. Most of the engineering value of HTTP is in agreeing on what the methods, status codes, and headers mean.

  • Methods have semantics. GET is safe (no side effects) and idempotent (calling twice = calling once). PUT and DELETE are idempotent. POST is neither — the most common bug in REST APIs is making writes GET-able, which means a web crawler can issue them.
  • Status codes have categories. 2xx success, 3xx redirect, 4xx client error (you sent something bad), 5xx server error (we screwed up). Senior engineers memorise the exact code for the common cases: 200 OK, 201 Created, 204 No Content, 301 permanent redirect, 304 Not Modified, 400 Bad Request, 401 Unauthorized (sic), 403 Forbidden, 404 Not Found, 409 Conflict, 410 Gone, 422 Unprocessable Entity, 429 Too Many Requests, 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.
  • Headers control caching (Cache-Control, ETag, If-None-Match), content negotiation (Accept, Accept-Language), conditional requests, and the many security headers (Chapter 13). The header layer is where most of the protocol's real power lives.

Idempotency and the safety properties

Safe means the method doesn't change state. Idempotent means calling it N times has the same effect as calling it once. These are under-appreciated and central to building reliable systems on top of an unreliable network. If a client sends a request and the network drops the response, the client doesn't know whether the request succeeded. If the request is idempotent, the client can safely retry. If it's not, the client has to either treat it as failed (and possibly duplicate work) or as succeeded (and possibly lose data). Chapter 12 returns to this in depth; for now, design PUT and DELETE idempotent, and give POST endpoints an Idempotency-Key header so they can be too.

The unbounded retry storm
A client retries on 5xx errors. The server is overloaded and returns more 5xx errors. The client retries more aggressively. The server gets even more overloaded. This is a retry storm, and it's how minor blips become outages. Two protections: (1) the server returns Retry-After and 429/503 to push back, (2) the client retries with exponential backoff plus jitter and gives up after a budget. Both are Chapter 12 patterns; the seed is in this chapter.

WebSockets, SSE, and the bidirectional question

HTTP is request/response. Sometimes you want the server to push to the client.

  • Long polling. Client sends a request; server holds it open until there's something to say, then responds. Client immediately makes another request. Works everywhere; wastes a connection per client.
  • Server-Sent Events (SSE). A regular HTTP response that never closes, with the server writing data: lines as events occur. Server-to-client only, runs over HTTP/2 cleanly, simple to implement. Underused.
  • WebSockets. A protocol upgrade (over HTTP/1.1) into a full-duplex framed binary channel. Client and server can both push. The right answer for chat, live editing, and gameplay. Adds complexity: it's not HTTP after the upgrade, so it doesn't respect HTTP intermediaries, caching, or many security controls.
  • WebTransport / gRPC streaming. Newer choices for bidirectional streams over HTTP/2 or HTTP/3.
Field practice
Three tools to keep within reach: curl -v (full visibility into HTTP requests, headers, TLS), dig (DNS introspection), tcpdump or Wireshark (the packet truth). When a service is misbehaving and the logs are uninformative, tcpdump on the host or sidecar will show you what's actually on the wire — connection resets, slow handshakes, missing data — and frequently the answer is something the application can't see from inside the language runtime.
```

Chapter 04 / Architecture

Monolith, modular monolith, microservices — and how to choose.

The architecture wars of the 2010s gave us two simplifications: "monoliths are bad" and "microservices are the future." Both are wrong, and engineers who absorbed them uncritically built systems that are now slowly being reverted. The real lesson of the last decade is more subtle: system shape should follow team shape, transaction shape, and failure-domain shape — not fashion.

```

The shapes you'll encounter

  • Monolith. One process, one deployable, one database. Internal calls are function calls. All state is consistent because it's all in one place. Refactoring across modules is a compiler problem, not a coordination problem. This is the right starting point for almost every product.
  • Modular monolith. Still one deployable, still mostly one database — but the codebase is divided into modules with explicit, enforced boundaries. Module A can call module B's public API but not its internals. Schemas are owned per module. You get most of the discipline of microservices without the operational cost.
  • Service-oriented architecture (SOA). The 2000s pattern. Coarse-grained services (Order Service, Inventory Service, Billing Service) usually communicating via an enterprise service bus. The bus often became the bottleneck.
  • Microservices. Many small services, each owned by a team, each with its own datastore, communicating over HTTP/gRPC/queues. Independent deploys, independent scaling, independent failure modes. Distributed system problems multiply with service count.
  • Event-driven architecture. Services communicate primarily by publishing events to a log (Kafka, Pulsar). Consumers subscribe to what they care about. Coupling is asynchronous and through schema. Excellent for analytics and integration; harder for synchronous user-facing flows.
  • Serverless. Functions deployed without explicit server management, scaled and billed per invocation. Best fit for sporadic, embarrassingly-parallel workloads (image processing, webhooks, glue code).

The case for starting monolithic

Microservices solve organisational problems by making teams independently deployable. Three teams that need to ship without coordinating release windows benefit from three services. One team building a product nobody is using yet does not. The early-stage microservices anti-pattern goes like this:

  1. Three engineers split the system into eight services because they read a blog.
  2. Adding a field now touches three services, three deploys, three pull requests.
  3. Latency increases (network hops between services).
  4. Bugs increase (now distributed: partial writes, retry storms, version skew).
  5. Velocity collapses. The team rewrites it back into a monolith eighteen months later.

The senior engineer's instinct is to defer the split. Build a monolith, keep the modules clean, and split only when there's a real reason: a team boundary, a scaling pressure on a specific component, a need for an independent failure domain. Don't split for the sake of "clean architecture."

When to actually split

Useful triggers — any one of these is reason enough:

  • Different scaling shape. The image-resize endpoint needs 100× the CPU and 10% the memory of the rest. Splitting lets you scale them independently.
  • Different release cadence. The payments path ships once a month with SOC 2 review; the marketing page ships ten times a day. Coupling those releases is worse than the operational overhead of two services.
  • Different failure domain. The legacy customer-import job is memory-hungry and prone to OOMs. Co-locating it with the request-handling tier means an import bug takes down the API.
  • Team independence. Two teams keep stepping on each other's deployments. Split the system along Conway's lines.
  • Polyglot pressure. The ML team wants Python and the rest of the company is on Go. A service boundary is also a language boundary.

Hexagonal architecture: the internal boundary that matters

Whether you choose monolith or microservices, the most important architectural decision happens inside a single service: the boundary between the domain and the infrastructure. Hexagonal architecture (Alistair Cockburn, 2005; also called Ports & Adapters, also Clean Architecture in Uncle Bob's framing) says: write your domain logic to depend only on interfaces (ports) you define. Implement those interfaces with adapters that talk to the database, the message queue, the third-party API.

The benefit is testability and changeability. Want to test the order pricing without spinning up a database? Inject an in-memory repository implementing the port. Want to swap Stripe for Adyen? Write a new adapter against the same payment port; the domain doesn't know. Want to move from PostgreSQL to DynamoDB? Same trick. This is the architectural pattern that makes the rest of this manual practical — every chapter from caching to messaging assumes you can swap an implementation without touching domain code.

CQRS and event sourcing: powerful, often overused

CQRS (Command Query Responsibility Segregation) means: use one model for writes (commands) and a different one for reads (queries). The write side optimises for correctness and validation; the read side optimises for query shape. They can even use different databases.

Event sourcing means: don't store current state — store the sequence of events that produced it. Current state is a fold over events. This gives you an audit log for free, the ability to time-travel, and a natural fit with messaging — but it makes simple "where is row X" queries hard, and rebuilding projections is operationally non-trivial.

Both patterns are powerful and both are routinely over-applied. Reach for them when the domain genuinely demands them — financial ledgers, audit-heavy workflows, complex temporal queries — and resist the urge otherwise. A CRUD app with event sourcing is a CRUD app where every operation is mysteriously eight times more code.

Conway's Law: the architecture you ship is the org chart you have

Melvin Conway, 1968: "Organizations design systems that mirror their communication structure." Three teams build a three-tier system; ten teams build ten microservices; one team builds one binary. The corollary, inverse Conway's manoeuvre, is the most useful organisational insight in software: shape the team boundaries you want first, and the architecture will follow. Trying to impose an architecture perpendicular to the org chart fails reliably.

Independently from monolith-vs-microservice, services talk to each other in two fundamentally different ways: synchronously (request/response, blocking until reply) and asynchronously (publish an event or message, continue without waiting).

The mistake to avoid: chains of synchronous calls. Service A calls B calls C calls D synchronously. REST — the lingua franca
```

```
REST (Representational State Transfer) is what Roy Fielding described in his 2000 dissertation, but most APIs labelled "REST" are not strictly RESTful — they are JSON-over-HTTP with resource-shaped URLs. That's fine. The conventions are what matter:

  • Resources, not actions, in URLs. POST /users/123/orders, not POST /createOrderForUser?id=123. The HTTP method is the verb.
  • HTTP methods carry semantics. GET reads. POST creates (and is non-idempotent). PUT replaces (and is idempotent). PATCH partially updates. DELETE removes.
  • Status codes are the protocol. 2xx for success, 4xx for client error, 5xx for server error. Do not return 200 with {"error": "..."}; that defeats every HTTP intermediary that exists.
  • Pagination, filtering, sorting are query parameters. GET /orders?status=pending&page_size=50&cursor=eyJ...

Pagination: offset vs cursor

Offset pagination (?page=3&size=20) is easy to implement and broken at scale: OFFSET 10000 makes the database scan past 10,000 rows it'll discard. It also misses rows when items are inserted between requests. Cursor pagination — "give me items after this opaque cursor" — is the right answer for any list that grows. The cursor encodes the sort key (e.g. created_at + id base64-encoded); lookups become WHERE (created_at, id) < (?, ?) ORDER BY ... LIMIT 20, which uses an index and stays fast at any page depth.

Versioning: when, where, how

You will eventually need to change an API in a breaking way. Plan for it. Three mainstream strategies:

  • URL path versioning (/v1/users, /v2/users): most operationally obvious. Easy to route, easy to deprecate. The default for most public APIs.
  • Header versioning (Accept: application/vnd.api+json;version=2): cleaner URLs, harder to discover and route. Strong fit when you control all clients.
  • Date-based versioning (Stripe's approach): every API call resolves against the version date in the API key. Best UX for clients; complex to implement (every version's behaviour must coexist server-side).

The rule above all: never break v1 silently. Either preserve backwards compatibility (by addition only — new fields are fine, removed or renamed fields are not) or ship a new version. Coordinated deprecation with timelines, deprecation headers, and a sunset date is the professional move.

Idempotency keys

For any non-idempotent endpoint that money can flow through, accept an Idempotency-Key header. Store the key with the response for some window (24h is common). On retry with the same key, return the original response without re-executing the operation. Stripe popularised this pattern; every payment API uses it now. Without it, network retries become duplicate charges. (Chapter 12 returns to idempotency in depth.)
```

```
OpenAPI and contract-first development

  • Contract testing: tests that confirm your server's responses match the spec.

Rate limiting and quotas

Every public endpoint needs a rate limit. Two algorithms cover most cases:

  • Token bucket. Each client has a bucket of N tokens that refills at R tokens/second. Each request consumes a token; if the bucket is empty, the request is rejected. Allows controlled bursts. Most common.
  • Sliding window log/counter. Count requests in the last W seconds; if over limit, reject. Smoother, more memory.

Communicate limits to clients via headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, and on rejection, 429 Too Many Requests with Retry-After. The IETF RateLimit-* headers (RFC 9745) are the standard you should adopt for any new API.

Field practice
Two contracts every senior engineer maintains: (1) the API contract — the OpenAPI/proto/SDL file that's part of the PR review, with CI breaking on incompatible changes; (2) the deprecation contract — a Sunset header policy, deprecation timelines published with the docs, and a metric on every endpoint counting how many callers are still using the deprecated version. Relational databases — the technology you cannot outgrow.
```

For thirty years engineers have predicted the death of the relational database. Each generation found a successor (object databases, XML stores, document databases, key-value stores, "NewSQL"), and each generation eventually rediscovered why the relational model won: it separates the logical data model from the physical layout, the query optimiser finds plans you didn't think of, and transactions give you guarantees that distributed systems cannot match. PostgreSQL is, in 2026, the default backend database. You should know it well.

```

The relational model — and why it works

The relational model is two ideas. First: data is a set of relations (tables), each a set of tuples (rows) over a fixed set of attributes (columns). Second: you query by describing what you want, not how to fetch it — the database figures out the access path. The first idea is normalisation; the second is declarative querying. Together they are the foundation of most backend storage.

Normalisation reduces redundancy and update anomalies. The classical forms (1NF, 2NF, 3NF, BCNF) are the rules; the practical heuristic is "every fact lives in exactly one place." Customer name lives in customers, not duplicated in every orders row. Address lives in an addresses table if it varies, not embedded in the customer.

Denormalisation is the deliberate violation of these rules for performance: you duplicate a value (the order total cached on the order row, the customer name copied onto the invoice) when computing it on the fly is too slow or read patterns demand locality. Denormalise only after measuring, and always with a plan for keeping the duplicates in sync.

Indexes — the single biggest performance lever

An index is a separate data structure that maps column values to the rows that contain them, letting the database find rows without scanning the whole table. The default index in every major database is a B-tree (technically a B+ tree): a balanced tree with hundreds of children per node, leaves linked in order. Lookups, range scans, and ordered iteration are all O(log n).

You need to know:

  • The primary key index already exists. In MySQL InnoDB and SQL Server, the primary key is the table's physical order (clustered index). In PostgreSQL, the heap is unordered and the PK is a separate B-tree.
  • Compound indexes on (a, b, c) are useful for queries filtering on a, on a AND b, and on a AND b AND c — but not on b alone or c alone. Column order matters.
  • Covering indexes include all columns a query needs, so the database never has to fetch the row from the heap. The PostgreSQL INCLUDE clause and MySQL's "covering index" mechanism do this explicitly.
  • Partial indexes index only rows matching a predicate (WHERE deleted_at IS NULL). Smaller, faster, useful for "active records."
  • Expression indexes index LOWER(email) or (created_at::date) for queries that filter on the expression.
  • Specialty index types: GIN (PostgreSQL) for arrays, JSONB, full-text; GiST for geometric and full-text; BRIN for very large append-only tables ordered roughly by insertion time; hash indexes for equality-only on huge tables.

Indexes are not free

Every index slows writes — every INSERT, UPDATE on indexed columns, and DELETE must update every relevant index. A table with twelve indexes can have its insert rate cut by an order of magnitude. Senior engineers prune unused indexes: 

-- PostgreSQL: find indexes that have never been read
```

SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE ’%_pkey’
ORDER BY pg_relation_size(indexrelid) DESC;
```

EXPLAIN — the most important command in SQL

EXPLAIN ANALYZE (Postgres) or EXPLAIN ANALYZE FORMAT=TREE (MySQL 8+) shows you the plan the query optimiser chose and how each step actually performed. Read top to bottom:

  • Seq Scan = full table scan. Fine for small tables, alarming for large ones.
  • Index Scan = walk an index, then look up each row in the heap.
  • Index Only Scan = the index covered the query. Fastest.
  • Bitmap Index Scan + Bitmap Heap Scan = combine multiple indexes, then do one pass over the heap. Excellent for OR conditions.
  • Nested Loop / Hash Join / Merge Join = three join algorithms. Hash for big symmetric joins; nested loop when one side is tiny; merge for pre-sorted inputs.

The numbers to watch: actual rows vs estimated rows (a 10× mismatch means the planner has bad stats — run ANALYZE), and the wall-clock time of each node. Most slow-query mysteries reduce to "the planner expected 100 rows, got 1,000,000, and chose the wrong join."

The N+1 problem — the most common ORM bug

Code like this looks innocent: 

for user in users:
print(user.name, user.orders.count())   # issues 1 query per user

If users has 1000 rows, this runs 1 + 1000 queries. Multiply by realistic table sizes and the database is on fire. Every ORM has the same trap and every ORM provides the fix: eager loading, join fetch, prefetch, preload, depending on dialect. Senior engineers know to inspect the SQL their ORM is generating — enable query logging in development, watch for unexpected query counts, and lean on tools like pgBadger, pg_stat_statements, or APM query analytics in production.

Connection pools — the resource you'll forget to size

Every database connection consumes memory on the server (1–10 MB in PostgreSQL, depending on configuration). Opening a connection takes a TCP handshake plus an authentication round-trip — easily 5–20 ms. Doing that per request is suicidal.

Connection pooling means your application opens N connections at startup and reuses them. Two layers, both useful:

  • In-process pool: HikariCP (Java), node-postgres pool, asyncpg pool. Size = concurrent queries you can run, not concurrent requests you can handle. A small (10–20) pool is usually right.
  • External pool: PgBouncer in front of PostgreSQL, ProxySQL in front of MySQL. Multiplexes thousands of application connections onto a smaller pool of backend connections. Essential when you have many application instances.

Sizing rule of thumb (from the classic HikariCP wiki): connections = (core_count * 2) + effective_spindle_count. The instinct to set it to 200 is wrong; more connections almost never mean more throughput, because the CPU bottleneck is the same.

Schema migrations — the safe way

Production schemas change. They have to be migrated without downtime. The rules:

  1. Never block writes during a deploy. Adding a column is fast in Postgres (since 11, default-valued adds are constant-time). Adding a column with a complex default to a 100M-row table can lock the table for hours.
  2. Expand, migrate, contract. Add the new column/table first. Deploy the code that writes to both old and new. Backfill the new from the old. Deploy code that reads from new. Stop writing the old. Drop the old. Five deploys, zero downtime.
  3. Never rename a column in place. Add the new, dual-write, switch reads, drop the old. Trying to rename in one migration breaks every running pod that has the old schema cached.
  4. Backfill in batches. Don't UPDATE entire_table SET ... — it locks for the duration and blows out the WAL. Loop: update 10,000 rows, commit, sleep, repeat. Tooling like pg-osc, gh-ost, pt-online-schema-change does this for you.

Migration runners (Flyway, Liquibase, Alembic, golang-migrate, Atlas, Sqitch) version your schema and apply migrations in order. Pick one early and stick with it. The team that manages schemas by SSHing to prod and running ALTER statements is the team about to lose its database.

Read replicas — and the lag that bites

A read replica is a database that follows the primary's WAL (write-ahead log) and serves read queries. Replicas scale read throughput linearly with replica count, at the cost of a few milliseconds of lag in steady state — and potentially seconds during write spikes.

The trap: read-after-write inconsistency. User submits a form (write to primary) and is redirected to a page that reads (from replica). If the replica hasn't caught up, the user sees stale data. Two fixes:

  • Read-your-writes routing: route the next read from a session to the primary if a write happened recently.
  • Synchronous replication for critical writes + replica-after for background reads. Both halve write throughput; use sparingly.

Sharding: only when you must

A single PostgreSQL or MySQL primary on modern hardware handles enormous workloads — tens of thousands of writes per second, tens of terabytes of data. Most companies will never outgrow it. If you do, the options are:

  • Vertical scaling: bigger box. Cheap in engineering, expensive in cloud bills, and there's a ceiling.
  • Functional sharding: split by feature — orders on one cluster, billing on another. Easy when the boundaries are clean.
  • Horizontal sharding: split rows of a single logical table across many physical clusters by a shard key (user_id, tenant_id). Hard. Done well by Vitess, CockroachDB, Citus, Aurora.

Sharding has irreversible consequences: cross-shard transactions become two-phase commits or sagas; joins across shards become application-level loops; many query patterns that were free now require scatter-gather. Reach for a managed distributed SQL system (CockroachDB, Spanner, TiDB, YugabyteDB) before you build sharding yourself — it's one of the most catastrophe-prone things a backend team can attempt.

Field practice
Every PostgreSQL-backed service should have these four queries bookmarked: pg_stat_activity (what's running now), pg_stat_statements (what runs the most), pg_locks (who's blocking whom), pg_stat_user_indexes (which indexes earn their keep). The answer to most performance mysteries is in those four views before it's anywhere else.
```

"NoSQL" is a marketing umbrella over four genuinely different data models. The 2010s mistake was treating them as drop-in replacements for relational databases; the 2020s correction is treating each as a specialised tool for a specialised problem. Key-value: the simplest abstraction

```
A key-value store is exactly what it says: get(key) → value, put(key, value). No schema, no query language, no joins. The simplicity is the feature — it makes the system trivially shardable (consistent hash by key) and the performance predictable.

Two important sub-families:

  • In-memory KV stores (Redis, Memcached, Aerospike). Microsecond latencies, used as caches (Chapter 9), rate limiters, leaderboards, ephemeral session stores. Redis has grown well beyond pure KV — it has lists, sets, sorted sets, streams, HyperLogLog, and Lua scripting — into a "data structures server."
  • Persistent KV stores (DynamoDB, FoundationDB, etcd, RocksDB). Durable, scaled, often the primary store for serverless workloads. DynamoDB in particular underpins a vast fraction of AWS infrastructure.

The skill with a KV store is access pattern design. You query by key, so the key has to encode every dimension you care about. DynamoDB's single-table design pattern — putting many entity types in one table with composite keys like USER#123 / ORDER#789 — is the canonical example. It's powerful and counter-intuitive to anyone trained on relational thinking.

Document stores: JSON with indexes

A document store treats each row as a JSON-like document with arbitrary nested structure. MongoDB is the dominant example; CouchDB, Couchbase, and Firestore round out the field. Key features:

  • Schema-flexible: each document can have different fields, evolving over time without migrations.
  • Nested access: query and index subfields and arrays (db.orders.find({"items.sku": "X"})).
  • Single-document atomicity: writes to one document are atomic; cross-document transactions exist in modern MongoDB but are deliberately limited.

Best fit: data that's inherently document-shaped — product catalogues with variable attributes, user-generated content with optional fields, denormalised aggregates ready for one-shot read. Bad fit: data with many many-to-many relationships and varied join patterns. The temptation to embed everything ("the order document contains the customer, the items, the shipping address, the payment...") leads to duplication and update anomalies — the same problems relational normalisation was invented to solve. Use embedding when the embedded data is read together and written together; reference (a key, look it up) otherwise.

Modern PostgreSQL's JSONB type closes much of the document-store gap: you get nested JSON with GIN indexes on subfields, all inside a relational database with real transactions and joins. For new projects, "Postgres with JSONB" is increasingly the pragmatic default over a separate document database.

Wide-column: the write-optimised shape

Cassandra and its descendants (ScyllaDB, AstraDB) are designed for one workload above all: high-throughput writes spread across many machines. The data model is a row identified by a partition key, with rows in the partition sorted by clustering keys. Within a partition, you can store millions of values and read ranges efficiently.

The strength: linear scale-out (add nodes, throughput goes up), no single point of failure, tunable per-query consistency. The weakness: you query the way you stored. There are no ad-hoc queries that don't include the partition key; secondary indexes are a footgun; joins don't exist. Schema design is dominated by listing every query the application will run, and shaping a table for each one.

Right fit: time-series at scale (IoT telemetry, log/event ingestion), high write throughput where reads always go through known keys (chat history, activity feeds), systems where multi-datacenter active-active is a requirement. Wrong fit: anything that needs flexible queries you didn't predict at design time.

Graph databases: when the relationships are the data

A graph database stores nodes and edges as first-class objects. You query with traversal languages (Cypher in Neo4j, Gremlin in TinkerPop) rather than joins: 

// "Find people two hops from Alice who like coffee."
```

MATCH (alice:Person {name: “Alice”})-[:KNOWS*2]-(friend)
WHERE (friend)-[:LIKES]->(:Drink {name: “Coffee”})
RETURN friend.name

The same query in SQL would be a self-join multiplied out — possible but ugly and slow past a few hops. Graph databases shine when traversal depth matters (fraud rings, recommendation graphs, dependency analysis, knowledge graphs). They are a poor general backend store; treat them as a specialised analytical tool.

```

Search engines: a fifth family worth knowing

Elasticsearch, OpenSearch, and Solr aren't strictly NoSQL but live in the same conceptual neighbourhood. They are inverted-index document stores optimised for full-text search, ranking, aggregations, and analytics. Strengths: search relevance, fuzzy matching, faceted search, dashboards. Weaknesses: not a source-of-truth store (eventual consistency, lossy under failure), expensive to operate at scale, primary indexer is a single-threaded bottleneck per shard.

The standard pattern: store source-of-truth data in a relational database; replicate into Elasticsearch (via CDC or change-feed) for search and analytics. Querying patterns where users type free text — "search for ..." — almost always want a real search engine, not a SQL LIKE '%query%'.

Time-series databases

Time-series workloads (metrics, sensor data, financial ticks) have a specific shape: append-mostly writes, ordered by time, queried by ranges with aggregations. Dedicated systems (InfluxDB, TimescaleDB, Prometheus, ClickHouse) optimise hard for it — columnar storage, time-bucketed compression, downsampling, retention policies. ClickHouse in particular has become the default for log/event analytics at scale; TimescaleDB layers the same patterns on PostgreSQL.

Vector databases — the LLM-era addition

Vector databases (Pinecone, Weaviate, Qdrant, Milvus, plus pgvector for Postgres) store embeddings — dense floating-point vectors — and provide approximate nearest-neighbour search. They are the storage layer for semantic search, recommendation, and retrieval-augmented generation. The interesting technical content is in the index structures: HNSW (Hierarchical Navigable Small World) and IVF (Inverted File) with product quantisation are the dominant choices, each trading recall against speed and memory.

For most backends with modest vector workloads, pgvector in PostgreSQL is the right starting point — keep your data in one place. Reach for a dedicated vector database only when scale (billions of vectors), latency (single-digit ms), or feature richness (hybrid search, filters at scale) demands it.

Polyglot persistence — used responsibly
A mature system often has: PostgreSQL for transactional data, Redis for caching and counters, Elasticsearch or Algolia for search, ClickHouse or BigQuery for analytics, S3 or GCS for blob storage, Kafka or Kinesis for events. That's a lot of stores. The cost is operational — each is one more thing to monitor, secure, back up. The principle: only add a store when an existing one is genuinely the wrong tool for the job, not because adding a database feels like progress. Most companies will overspend a year of engineering on infrastructure their workload didn't need.

Choosing in practice

A pragmatic decision tree:

  1. Start with PostgreSQL. It does 95% of what most products need, including JSON, full-text search, time-series (with TimescaleDB), and vectors (with pgvector).
  2. Add Redis once you need caching, rate limits, distributed locks, or pub-sub ephemeral data.
  3. Add a search engine (Elasticsearch / Algolia / Meilisearch) when full-text search relevance is a product requirement, not a nice-to-have.
  4. Add a warehouse (Snowflake / BigQuery / ClickHouse) when analytics queries start interfering with OLTP performance.
  5. Reach for a wide-column store (Cassandra / Scylla) only when write throughput on a well-understood access pattern exceeds what a vertically-scaled Postgres can do.
  6. Reach for a graph database only when traversal queries are a primary feature, not an occasional report.
Field practice
Before adding a new database to your stack, write the access patterns down. If three of them can be served by Postgres with the right index, and only one really wants Cassandra, you usually do not have a Cassandra workload yet — you have one query that should be cached or materialised. Promoting workloads to new stores prematurely is a leading cause of platform engineering teams growing faster than product engineering teams.
```

Transactions, isolation, and the concurrency problems they don't solve.

Transactions are the single most powerful tool a database gives you, and the single least-understood feature of most production systems. Engineers learn "ACID" as a slogan, pick an isolation level by copying the previous service, and discover three years later that their idea of "atomic" was always weaker than they thought. This chapter is the bottom-up version: what ACID actually guarantees, what the isolation levels actually do, and which concurrency bugs survive them.

```

ACID, explained for adults

  • Atomicity — all the writes in a transaction commit, or none do. If anything goes wrong, the database undoes the changes. Atomicity is about nothing partial.
  • Consistency — the transaction takes the database from one valid state to another. "Valid" here means satisfies all constraints (foreign keys, CHECKs, unique indexes) plus any invariants you've expressed. Consistency is largely the application's responsibility; the database enforces the constraints you defined.
  • Isolation — concurrent transactions appear to run one at a time, or at least pretend to. This is the property that almost everyone gets wrong; see below.
  • Durability — once a transaction is committed, it survives crashes. Practical durability depends on fsync hitting the disk and (for HA) the write being replicated. synchronous_commit = off in Postgres trades durability for write throughput; understand the trade before flipping it.

Isolation levels — the ladder

Concurrent transactions can interfere in four classical ways:

  • Dirty read: a transaction sees another transaction's uncommitted write.
  • Non-repeatable read: a transaction reads a row twice and sees different values, because another transaction committed in between.
  • Phantom read: a transaction runs the same range query twice and gets different rows.
  • Lost update / write skew: two transactions read the same data, each decides what to write, and the second silently overwrites the first.

The SQL standard defines four isolation levels in terms of which of these are prevented:
```

```
The fixes for write skew

Three real solutions:

  1. Row-level locking with SELECT ... FOR UPDATE. Locks the row for the duration of the transaction; the second transaction waits. Works at Read Committed.
  2. Atomic SQL. Rewrite the operation so the check and the write happen in one statement: UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 50. The database's row-level lock during the UPDATE serialises it. Check the row count to confirm the update happened.
  3. Serializable isolation. Postgres's Serializable Snapshot Isolation (SSI) detects conflicts at commit time and aborts the loser with a serialization_failure. Your code must retry. Real serialisable correctness for a modest throughput cost; underused.

For money, identity, and inventory — anywhere correctness beats throughput — atomic SQL or Serializable isolation is the default. Optimistic locking (a version column on the row, compare-and-swap via UPDATE) is a fourth approach that works well when contention is rare.

MVCC — how Postgres actually does it

PostgreSQL and most modern databases implement isolation via Multi-Version Concurrency Control. Every row has hidden columns (xmin, xmax) recording the transaction that created and the transaction that deleted it. A read sees the version of each row that was visible to it when its transaction started; concurrent writers create new versions without blocking readers.

Implication: readers never block writers and writers never block readers. The cost is that obsolete row versions accumulate and must be cleaned up. PostgreSQL calls this vacuum; tuning autovacuum on write-heavy tables is one of the standard Postgres operational concerns.

Pessimistic vs optimistic concurrency

Two strategies you'll choose between every time you build a stateful endpoint:

  • Pessimistic. Acquire a lock before reading the data you'll modify (SELECT ... FOR UPDATE). Other writers wait. Correct, simple, but creates lock contention; deadlocks become a real concern with multiple resources.
  • Optimistic. Read without locking. When you write, check the row hasn't changed since you read it (using a version column or a timestamp). If it has, retry the whole transaction. Best when conflicts are rare; degrades quickly when they're common.

Choose based on contention: hot rows (the popular product's inventory counter, the single ledger row everyone debits) want pessimistic; long workflows where collisions are rare want optimistic. Implement both well and you can usually tune your way out of contention problems before they become outages.

Deadlocks: real, common, recoverable

Two transactions hold locks the other needs and wait for each other forever. Modern databases detect deadlocks and abort one transaction with a deadlock error; your application must retry. The avoidance recipe:

  • Always acquire locks in the same order. If transactions A and B both lock rows {1, 2}, both must lock 1 before 2. Order by primary key.
  • Keep transactions short. A transaction holding locks while it waits for a slow HTTP call is a deadlock waiting to happen — and a serial throughput killer.
  • Never make external calls inside a transaction. No HTTP, no Kafka, no email API. Commit first, then call.

Distributed transactions: don't, mostly

A transaction spanning two databases (or a database and a message queue, or two services each with its own database) is a distributed transaction. The historical solution, two-phase commit (XA), is correct but operationally fragile — a coordinator failure can leave participants stuck holding locks indefinitely, requiring manual intervention. Most modern systems avoid 2PC entirely.

The pragmatic alternatives:

  • Sagas — a sequence of local transactions, each with a compensating action. If step 3 fails, run the compensations for steps 1 and 2. (Chapter 12.)
  • The outbox pattern — write your event to an "outbox" table in the same transaction as your domain write. A separate process polls the outbox and publishes to Kafka. You get atomicity between database and message queue without 2PC.
  • Eventual consistency — accept that two systems will diverge briefly, and design for reconciliation rather than prevention.
```

```

Long-running transactions: the silent killer

A transaction that stays open for minutes (an analytical query, a misconfigured framework, an interactive session left idle) holds locks and prevents MVCC cleanup. In Postgres, that means dead tuples accumulate, autovacuum stalls, table sizes balloon. Symptom: a table that grows for no reason; a host running out of disk; queries getting slower with no schema changes.

Set a server-side idle_in_transaction_session_timeout and statement_timeout. Both should be small. A misbehaving service will be terminated with a clear error rather than slowly destroying the cluster.

Transactions inside loops
Common bug: opening a transaction, looping over results from another query, and doing one INSERT per iteration. Three problems: (1) the outer query holds a cursor open across writes — version conflicts; (2) the transaction grows long, holding locks; (3) you do N separate index updates instead of one bulk. The fix is to collect the inputs, close the outer transaction, and do a batched insert: INSERT INTO ... VALUES (...), (...), (...) or COPY for large volumes.
Field practice
Two invariants every senior backend engineer enforces in code review: (1) no external I/O inside a database transaction; (2) no business invariant enforced by application-level "check then write" without explicit locking or an atomic UPDATE. Both rules feel pedantic until the day the outage retrospective traces straight back to one of them being broken.
```

Chapter 09 / Performance

Caching — fast on the happy path, terrifying on the unhappy one.

A cache is a faster, smaller copy of something slower and larger. Adding one is the easiest way to make a system fast, and the easiest way to make it incorrect. Phil Karlton's observation that "there are only two hard things in Computer Science: cache invalidation and naming things" is older than half of this manual's readers, and still annually validated by production incidents. Treat caches with care.

```

The cache hierarchy in a typical backend

A single request can traverse half a dozen caches before reaching anything authoritative. From outside to in:

  1. Browser cache — local to the user. Cache-Control: max-age=... on responses.
  2. CDN edge — Cloudflare, Fastly, CloudFront. Caches at hundreds of physical locations close to users.
  3. Reverse proxy / API gateway cache — Varnish, Nginx, your gateway. Local to the datacenter.
  4. Application-level cache — in-process LRU, often the fastest layer.
  5. Distributed cache — Redis, Memcached. Shared across application instances.
  6. Database buffer pool / page cache — the database's RAM. Most reads from a "warm" database never touch disk.

Each layer can serve a request faster than the next; each layer can also hand back stale or wrong data. Senior engineers think in terms of where authoritative state lives, what the invalidation contract is at each layer, and what happens when each layer fails.

Write strategies — the choices that determine consistency

How a cache and the underlying store stay in sync depends entirely on the write pattern you choose. The four classical patterns:

PatternWrite flowProperties
Cache-aside (lazy loading)Write to DB. Invalidate or update cache. Reads check cache first; on miss, read DB and populate.Default. Cache may briefly serve stale data; tolerant of cache failures.

Cache-aside is the right default. It tolerates a cache outage (just slow), it keeps the cache off the write path's critical correctness contract, and it makes the "what is true" question unambiguous: the database is. Other patterns have real uses but are operationally trickier.

The two cache-aside footguns

Cache-aside has two classic bugs.

First, the write-then-invalidate race:

  1. Thread A reads the cache, misses.
  2. Thread A reads from DB, gets old value.
  3. Thread B writes new value to DB.
  4. Thread B invalidates cache (no-op; nothing cached).
  5. Thread A populates cache with old value it read in step 2.

Now the cache holds a stale value indefinitely. The fix is versioned cache keys (include a version of the row in the key, so step 5 stores under a different key) or set-on-write with a TTL fence (the cache update only takes if a fresher value isn't already there).

Second, the thundering herd / cache stampede: a popular key expires and a thousand requests hit the database simultaneously to repopulate it. Three fixes, composable:

  • Probabilistic early expiration: let one of the requests refresh the cache when it's close to expiration, before it actually expires.
  • Request coalescing / single-flight: only one request per key is allowed to repopulate; others wait or return the stale value.
  • Stale-while-revalidate: serve the stale value while a background refresh runs.

TTL — the most powerful and most-abused setting

Every cached entry needs a TTL. Three considerations:

  • Stale tolerance. How wrong is the data allowed to be? A product catalog tolerates minutes. An inventory counter tolerates seconds, if that.
  • Backstop against bugs. Even with perfect invalidation, set a TTL so any leaked stale entry eventually disappears. "Forever" is a category of outage waiting to happen.
  • TTL jitter. Don't TTL everything for exactly 60 seconds — they all expire at the same time, causing a synchronized herd. Add random jitter (60s ± 10s).

Eviction policies

Caches are bounded; when full, something gets evicted. The policies:

  • LRU (Least Recently Used) — evicts whatever hasn't been touched longest. The classic default; good for most workloads.
  • LFU (Least Frequently Used) — evicts what's been accessed least often. Better for workloads with strong hot/cold separation.
  • TinyLFU / W-TinyLFU — the modern default in Caffeine, Ristretto. Combines LFU admission filtering with LRU eviction; near-optimal in practice.
  • FIFO / random — surprisingly competitive in some workloads, with much simpler implementation.
  • Volatile-TTL (Redis) — evicts the entry with the soonest expiration.

Redis — the Swiss Army cache

Redis is the de facto distributed cache for most stacks, and worth knowing well beyond GET/SET. Key features:

  • Data structures: strings, lists, sets, sorted sets, hashes, bitmaps, HyperLogLog, streams. Use the right one. A sorted set is a leaderboard; a hash is a per-user object; HyperLogLog is a cardinality counter in 12 KB.
  • Atomic operations: INCR, DECR, APPEND, SETNX. The basis for rate limiters, distributed locks, deduplication.
  • Pub/sub and streams: lightweight messaging without Kafka's complexity.
  • Lua scripting: run a script atomically on the server. The right pattern when "two operations must be one" — a check-and-set across multiple keys.
  • Persistence: RDB snapshots, AOF append-only file. Redis can be durable, but treat its primary role as a cache, not a database.
```

```

The distributed lock pattern (and why you shouldn't)

"I'll use Redis to acquire a distributed lock." Sounds simple; isn't.

The naive version — SET key value NX EX 30, do work, DEL key — has multiple failure modes:

  • If the work takes longer than 30 seconds, the lock expires while you still think you hold it. Another worker acquires it. Now both run.
  • If you crash before DEL, the lock holds for 30 seconds. Fine.
  • If you successfully DEL a lock that already expired and was re-acquired by someone else, you delete their lock. Bad.

The fixes (own-the-value pattern with a Lua script to delete-if-mine; lock renewal heartbeats; Redlock for multi-Redis quorum) are real but each introduces complexity, and Redlock specifically has been criticised by Kyle Kingsbury and Martin Kleppmann for relying on bounded clock drift that real systems don't guarantee. The senior take: if correctness actually matters, use a real coordination service (etcd, Zookeeper, Consul) that uses Raft or Paxos. Redis locks are for soft mutual exclusion where the occasional double-execution is tolerable.

HTTP caching — the layer most engineers ignore

The simplest cache to add to your service is the HTTP cache that already exists in every browser, CDN, and reverse proxy. Two response headers do most of the work:

  • Cache-Control: public, max-age=300 — anyone may cache, for 300 seconds.
  • ETag: "abc123" — opaque version tag. The next request includes If-None-Match: "abc123"; if unchanged, server replies with 304 Not Modified and no body.

For pages and assets that don't change per user, this is the single most powerful free optimisation available. A well-set Cache-Control on your CDN can absorb 99% of read traffic before it ever reaches your origin.

Caching is observable or not at all

Three metrics every cache must export:

  • Hit ratio. Hits / (hits + misses). Low ratios mean the cache isn't helping; investigate keys or TTLs.
  • Latency. Cache lookup p50/p99. A "cache" that takes 50ms is not a cache, it's another database.
  • Eviction rate. Evictions/sec. If high, the cache is too small for the working set.
The cache that hides the bug
A common production trap: the cache is good enough to mask a broken authoritative store. Reads work fine (from cache), but new writes fail or take forever — you only notice when the cache expires. Always alert on the cache's backing store latency in addition to the cache itself; a healthy cache hit ratio with a sick database is the shape of a slow-motion outage.
Field practice
Three rules: (1) The cache is never the source of truth. (2) Every cache entry has a TTL, including the ones you think don't need one. (3) Write the invalidation logic the day you add the cache — not the week it goes wrong. If you cannot articulate when each cached value becomes stale and how the cache learns about it, you don't have a cache. You have a bug.
```

Chapter 10 / Asynchrony

Messaging & streaming.

A synchronous call is a request for an answer right now. A message is a request for something to happen eventually, possibly by someone you've never met. The move from the first to the second is not a refactor — it is a change in the shape of your system. You give up the call stack and the immediate error; in return you get decoupling, buffering, replay, and the ability for one event to be heard by many. The bill is paid in operational complexity, and most teams underestimate it.

```

The two shapes: queue and log

Underneath every messaging product is one of two mental models.

A queue is a line. Producers append; consumers take items off and they are gone. Each message is delivered to one consumer (within a group), then deleted or acknowledged. This is the RabbitMQ / ActiveMQ / SQS shape. It is excellent for work distribution — give me a hundred jobs and a dozen workers and let the broker hand them out.

A log is an append-only file. Producers append; consumers read by remembering an offset. The broker doesn't delete on read — it deletes by retention policy (a week, a month, forever). The same message is naturally available to every consumer who wants it, and any consumer can rewind. This is the Kafka / Kinesis / Pulsar shape. It is excellent for streaming, event sourcing, and decoupled fan-out.

A great deal of confusion in distributed system design comes from treating one as the other. A log is not a slow queue; a queue is not a forgetful log. Pick deliberately.

Delivery guarantees: choose two, then suffer

Brokers promise one of three things, and the third is a polite lie.

At-most-once. Fire and forget. If the broker crashes between receiving and persisting, the message is gone. Use it for metrics, telemetry, and other things where losing a few is preferable to processing duplicates.

At-least-once. The broker acknowledges only after durable write; the consumer acknowledges only after successful processing. Retries on failure mean the same message may arrive twice. This is the default for serious systems — and it forces idempotent consumers.

Exactly-once. The broker, the producer, and the consumer cooperate so that every message is processed precisely once. Kafka markets this, and within Kafka — same cluster, transactional producer, idempotent producer ID, read-process-write inside one transaction — it is real. The moment your consumer has any side effect outside Kafka (a Postgres insert, an email, an HTTP call), exactly-once collapses back to at-least-once. The fix is not to chase the broker's marketing slide; it is to make your consumer idempotent and stop worrying about it.

Partitioning & ordering

A log is fast because it is partitioned. Kafka splits a topic into N partitions, each an independent append-only file living on different brokers, each with its own consumer in a group. Order is preserved within a partition, never across them.

Whatever key you partition on becomes your unit of order. Key by user_id and one user's events stay in order while different users parallelise freely. Key on something that doesn't matter — round-robin, random — and you get throughput but no order. Key on something coarse — tenant_id for a system where 1% of tenants drive 80% of traffic — and you'll have one partition red-hot and the others idle. This is the hot partition problem and it is the single most common Kafka mistake.

Consumer groups, offsets, and the rebalance

A consumer group is a set of processes reading the same topic cooperatively. Kafka assigns partitions to group members; if you have 12 partitions and 4 consumers, each gets 3. Add a fifth and Kafka rebalances: pauses everyone, reassigns, resumes. During rebalance no work happens. Frequent restarts, deploys, or slow consumers (that miss the heartbeat) cause rebalance storms — your throughput drops because the cluster spends its life reassigning instead of consuming.

Offsets — your bookmark in the log — are committed back to Kafka. Commit too early (before processing) and a crash means lost work. Commit too late and a crash means reprocessing. The standard pattern: process the message, then commit. Combined with idempotent handlers, this is correct and simple.

Dead-letter queues

A poison message — one that will fail every time, forever — will, in a naive at-least-once consumer, block the partition indefinitely. The fix is a dead-letter queue (DLQ): after N retries, ship the message to a side topic with the original payload, the failure reason, and the trace ID. The main consumer moves on; an operator investigates the DLQ.

A DLQ is a graveyard, not a wastebasket. Build an interface to inspect it, dashboards to alert when it's filling, and tooling to replay messages back into the main topic after a fix. A DLQ no one looks at is just a slow data loss.

The outbox pattern (again, because it matters)

You handle an HTTP request, write a row to Postgres, and need to publish an event to Kafka. You cannot do both atomically — they are different systems. If you write then publish and the publish fails, you lied to downstream. If you publish then write and the write fails, you fabricated an event.

The outbox pattern: write the event into an outbox table in the same transaction as the business change. A separate relay process (or Debezium reading the WAL) tails the outbox and publishes to Kafka, marking rows as sent. Atomicity is preserved inside Postgres; eventual delivery is guaranteed by the relay; idempotency on the consumer handles duplicates. This pattern is boring and correct. Use it.

Change data capture

Change data capture (CDC) turns your database's write-ahead log into an event stream. Debezium attaches to Postgres logical replication and emits one Kafka message per row changed; the same exists for MySQL binlog, MongoDB oplog, and SQL Server. CDC is how you replicate to a data warehouse, feed a search index, or build read models without scattering publish() calls through your code.

CDC is not free. Logical replication slots in Postgres hold WAL on disk until the consumer catches up; a stalled Debezium can fill your database disk and bring you down. Monitor slot lag like you monitor replication lag.

Stream processing

Once events flow as streams, you'll want to compute over them: aggregate, join, window. The tools sort into three tiers.

Light: Kafka Streams (Java library, no extra cluster), Faust (Python), ksqlDB (SQL on Kafka). Great for stateless or modestly stateful pipelines that live next to your services.

Medium: Apache Flink. Real stream processor with proper event-time semantics, watermarks, exactly-once via checkpointing, and large windowed state. Production-grade for serious analytics and CEP.

Heavy: Spark Structured Streaming, Beam. Closer to micro-batch; pick when you already run Spark for batch and want to unify code paths.

The thing every team gets wrong here: event time versus processing time. Events arrive late and out of order. A window "the last 5 minutes" computed on processing time silently miscounts when a batch arrives delayed. Use event time + watermarks if the answer needs to be right.

Treat messaging as a separate system with its own SLO, dashboard, and on-call runbook. Make every consumer idempotent and write down the idempotency key — message ID, business key, both. If your producer is a database, use the outbox; if you can't bear to use the outbox, you are not yet ready for events. Above all: do not adopt Kafka because it is on the architecture diagram of a bigger company. Adopt it the day a Postgres job table stops being enough — and not before.
```

Chapter 11 / Distributed systems

CAP, consensus & time.

A distributed system is what you get when a computer you didn't know existed stops you from doing your work. Lamport's old joke names the central problem: the machines you depend on are not yours, you cannot see them, and they may have failed in ways you cannot detect. Every chapter so far has nibbled at the edges of this — replication, consensus, partitions, ordering — and now we look directly at the theory that names the constraints. The names matter because they are how senior engineers spot a bad design before it ships.

```

CAP, correctly

Brewer's theorem says: in the presence of a network Partition, a system must choose between Consistency (every read sees the latest write) and Availability (every request gets a non-error response). It does not say "pick two of three"; the partition is not a choice — networks partition, that is a fact about the world. What you choose is what to do when they do.

A CP system, faced with a partition, refuses requests on the minority side rather than serve stale data. ZooKeeper, etcd, Spanner, MongoDB with majority writes — these will return errors rather than lie. An AP system serves both sides of the partition and reconciles later. DynamoDB with eventual consistency, Cassandra, Riak — these will answer everyone, possibly with conflicting versions.

Real systems are tunable, not binary. Cassandra lets you choose QUORUM reads and writes (CP-ish) or ONE (AP). DynamoDB has strongly-consistent reads as a flag. The interesting question is not "which letters does my database pick" but "for each operation, which letters do I pick".

PACELC: the rest of the story

CAP only describes behaviour during partitions. PACELC adds: else (in normal operation), you choose between Latency and Consistency. A strongly consistent system on a healthy network still pays for it — Spanner's strong reads cross regions; Postgres synchronous replication waits for the replica's ack. The real cost of consistency is not partition behaviour; it is the milliseconds added to every request, every day.

Consistency models, from strictest to laxest

"Eventually consistent" is the most abused phrase in distributed systems. There is a precise ladder.

They are about violating the cheap session guarantees: a user posts a comment and then doesn't see it on refresh. Read-your-writes via sticky sessions or read-from-leader for the original writer fixes 90% of the felt pain at a fraction of the cost of strong consistency.

Consensus & the Raft mental model

Consensus is the problem of getting N machines to agree on a value (or a sequence of values) despite some of them failing. Paxos solved it; Raft made it teachable. Every modern coordination system — etcd, Consul, CockroachDB, TiKV, Kafka's KRaft — is Raft underneath.

The Raft picture is small enough to hold in your head. One node is the leader. All writes flow through the leader, which appends to its log and replicates to followers. An entry is committed when a majority (quorum) has acknowledged it. Leaders send heartbeats; if followers don't hear one, a follower starts an election by becoming a candidate and asking peers for votes. A node grants its vote at most once per election term, so at most one candidate wins a majority.

The consequences are worth remembering. (1) Raft tolerates the loss of a minority — a 3-node cluster survives 1 failure, a 5-node survives 2. (2) Even numbers of nodes are a waste: 4 nodes tolerate the same failures as 3 (one) but require larger quorums (3 vs 2). (3) Every commit costs at least one round trip to a majority — co-locating your Raft cluster in one region matters. (4) Leader failover is not instant; expect a few seconds of write unavailability during election.

Time is a lie

You cannot trust System.currentTimeMillis() across machines. Wall clocks drift, get adjusted by NTP, leap seconds happen, and a VM migration can move a clock backwards. Two events with timestamps in the wrong order is not a paradox; it is normal.

Distributed systems use logical clocks instead.

Lamport timestamps: each process keeps a counter; increment on local events; attach to outgoing messages; on receive, set local = max(local, received) + 1. Result: if A causally precedes B, then ts(A) < ts(B). The reverse is not true — equal or ordered timestamps don't imply causality.

Vector clocks: each process keeps a vector of counters, one per process. You can now detect concurrent events (vectors are incomparable) versus causally ordered ones. This is how Dynamo-style systems detect conflicting versions.

Hybrid logical clocks (HLC): combine wall-clock and logical counter so timestamps are close to real time and still monotonic and causal. CockroachDB and YugabyteDB use HLC; if you're rolling your own ordering, this is the modern choice.

Spanner cheats by using TrueTime — physical clocks bounded by GPS and atomic receivers, with the database explicitly waiting out the uncertainty window before commit. Unless you run a planet-scale database, you don't get this. Use HLC.

Quorums & the N/R/W trick

Dynamo-style systems give you knobs. With N replicas, write to W of them and read from R. If R + W > N, every read overlaps every successful write — you'll see the latest value (modulo conflict resolution). N=3, W=2, R=2 is the classic sweet spot: tolerates one failure, modest latency, strong-ish consistency. N=3, W=1, R=1 maximises availability and minimises latency, but reads can be stale.

Conflict resolution under N/R/W: last-write-wins with wall clocks is wrong; it silently drops data when clocks skew. Use vector clocks and surface conflicts to the application, or use a CRDT, or design so conflicts cannot occur (single writer per key).

Split brain

A partition can put two nodes each convinced it is the leader. If both accept writes, you now have two divergent histories that cannot be merged. Prevention: quorum-based leadership (only the side with majority can elect a leader), fencing tokens (each leader gets a monotonically increasing epoch; storage rejects writes from an old epoch), and STONITH ("shoot the other node in the head") in stateful HA clusters.

Failure detection: the gray zone

The hardest distributed bug is not the down node — it's the half-down one. Network partial-failures (one direction works, the other doesn't), the GC-paused JVM that stops heartbeating for 30 seconds and then resumes, the disk that returns success but doesn't actually fsync. Heartbeat-based failure detectors trade off detection time for false positives; phi-accrual detectors (Akka, Cassandra) give a probability rather than a bool. The deeper truth: in an asynchronous network, you cannot reliably distinguish slow from dead. Design accordingly — every call has a deadline, every operation idempotent, every consensus quorum-based.

Test like Jepsen, or pay later

Kyle Kingsbury's Jepsen reports have, over a decade, found correctness bugs in nearly every production distributed database. The technique: inject network partitions and clock skews while running concurrent operations, then check the resulting history against a model of the claimed consistency level. If you build something distributed, run it under partitions and pauses before production. Tools like Jepsen and toxiproxy are how you do this without booking a customer outage.

Note
The eight fallacies of distributed computing (Deutsch & Gosling): the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, the network is homogeneous. Every distributed bug in your career will be one of these.
Field practice
Write the consistency model down for each operation, in plain prose: "reads from replica may be up to 200ms stale; the user's own writes are read from leader for 5 seconds after commit; payment authorisation is strongly consistent via the leader". Build mental models around quorums and epochs, not "the master". Test the system under partitions and pauses with a chaos tool before you ship; you will find bugs that take months in production otherwise. And when an engineer claims "we just need exactly-once" or "eventually consistent is fine", make them define eventually in milliseconds and describe what happens to a partitioned client. Vagueness here is how outages are born.
```

Chapter 12 / Resilience

Reliability patterns.

Distributed systems fail. Not occasionally; constantly, in small ways, all the time. A senior backend engineer is not someone whose code never fails — that engineer doesn't exist. They are someone whose code fails well: it times out promptly, retries safely, degrades gracefully, recovers cleanly, and tells you exactly what happened. The patterns below are the standard library of resilient design. Use them sparingly but use them on purpose; each one is debt against complexity that pays interest in uptime.

```

Always set a timeout

Every network call must have a timeout. There is no exception. The default in many HTTP clients — Java's old URLConnection, Python's requests without a timeout= argument — is to wait forever, and "forever" in production means until your thread pool fills, your connections exhaust, and your service falls over because one downstream got slow.

Set timeouts at both the connection and read phases. Cascade them: if your API has a 5-second SLO, the database call gets 3, the cache 50ms, the external API 1.5. The total of downstream timeouts must fit inside your own. This is the timeout budget, and it is the most neglected number in most architectures.

Retries: useful, dangerous

A retry is a bet that a failure was transient. Sometimes you win — a TCP reset, a momentary DNS hiccup, a 503 because a pod was rolling. Sometimes you lose: the downstream is overloaded, and your retries are the load that overloaded it. The retry storm is a classic outage amplifier — every layer retries 3 times, so a single failure causes 27 requests, and the system that briefly hiccuped collapses under the wave.

Three rules.

Only retry idempotent operations. Retrying a non-idempotent POST is how you charge the customer twice. Pair retries with idempotency keys (Ch. 8) so the server can deduplicate.

Exponential backoff with jitter. Sleep 100ms, then 200, 400, 800 — with random jitter so a thundering herd doesn't synchronise. The "full jitter" formula from AWS (sleep = random(0, base · 2^attempt)) is empirically the best behaviour under load.

Retry budgets, not retry counts. Don't retry every request 3 times; retry only if the recent error rate is below a threshold. When the downstream is on fire, the kindest thing is to stop hitting it.

Circuit breakers

A circuit breaker watches the failure rate on a downstream dependency. While failures are below a threshold, it is closed and traffic flows. Above the threshold, it opens: requests fail fast without even attempting the network call. After a cool-down it goes half-open — letting a probe through; success closes it again, failure reopens it.

The value of the breaker isn't speed; it's protection. A failing downstream that you keep hitting holds onto your threads, fills your connection pool, and turns a partial outage into a total one. The breaker lets you serve some traffic — perhaps with a fallback — instead of no traffic.

The trade-off: a too-eager breaker flaps; a too-lazy one doesn't help. Set thresholds on real measurements, not gut feel. Hystrix popularised this; Resilience4j, Polly, and Istio give you implementations today.

Bulkheads

A ship is divided into watertight compartments so a single hull breach can't sink it. A bulkhead in software is the same idea: isolate pools of resources so one slow dependency can't drain everything. Different thread pool for the flaky external API. Different database connection pool for the heavy report endpoint. Different rate-limit bucket per tenant.

Without bulkheads, one slow dependency holds every thread, every connection, every fibre until your whole service is unavailable — even for requests that never touch the broken thing. With bulkheads, the slow dependency degrades but the rest of the system keeps working. This is how you turn a P1 into a P3.

Backpressure & load shedding

When demand exceeds capacity, something gives. Without backpressure, queues grow, latencies explode, memory fills, the kernel kills processes. Backpressure is the system telling its callers "slow down" — by returning 429, by closing the TCP window, by pausing producers. Reactive frameworks (Reactor, Akka Streams, RxJava) encode backpressure end-to-end.

Load shedding is the opposite valve: rather than slow down accepting work, drop some. An admission controller refuses low-priority requests when CPU is over 80%, the queue is full, or the SLO is at risk. Counterintuitively, dropping 10% of requests can bring p99 latency back to normal when accepting them all would degrade everyone. Netflix's concurrency-limits library and Envoy's adaptive concurrency are off-the-shelf implementations.

Idempotency, revisited

Every reliability pattern in this chapter relies on the same primitive: the receiver must be safe under retries. The mechanism (idempotency keys, dedup tables, conditional writes) lives at the boundary of each service. Without it, every retry, every breaker probe, every replay carries the risk of doubling effects. With it, the system becomes safely retriable, and almost every other pattern composes cleanly.

Sagas: long-lived workflows without 2PC

A booking that reserves a flight, a hotel, and a car spans three services. Two-phase commit is not available. The saga pattern decomposes the workflow into local transactions plus compensating actions: if step 3 fails, you don't roll back step 1 — you execute a cancellation that semantically undoes it.

Two flavours.

Choreography: services publish events; other services react. Simple, no coordinator, but the workflow's logic is smeared across the codebase — nobody can answer "what happens after step 3?" without grepping.

Orchestration: a central orchestrator (Temporal, AWS Step Functions, Camunda) runs the workflow as code, calling each service and handling compensations. Easier to reason about, easier to test, the right default for non-trivial sagas. Temporal has become the de facto choice in 2025: durable execution where the orchestrator can crash and the workflow resumes from its last step.

Graceful degradation

Not every failure should be visible. A product page that can't fetch personalised recommendations should still render the product; the recommendation block becomes a generic fallback. A checkout that can't reach the loyalty service should still charge; loyalty points can be reconciled later. The pattern: identify what is core and what is enrichment, and design enrichment to be skippable.

Chaos engineering

Netflix's Chaos Monkey is a quarter-century-old idea now: deliberately break things in production so you discover the failures during business hours rather than at 3am. Modern practice: a quarterly game day where the on-call team kills a randomly chosen pod, blocks a region's network, or fills a disk; observe what happens; fix what surprised you. The goal is not to prove you're robust — it's to find where you're not.

Error budgets & SLO-driven reliability

Google SRE's killer idea: an SLO (e.g. 99.9% availability) implies an error budget — 0.1% of requests may fail per month. If you're burning your budget, slow new feature releases and invest in reliability. If you're well under, you can ship faster. This makes "reliability vs. velocity" a number, not an argument. We'll dig deeper in chapter 14.

Warning
Layering retries without coordination amplifies failures. Define at one layer where retries happen (typically the client SDK or the gateway), and disable them at the others. Putting retries in your handler, your client library, your service mesh, and your load balancer turns a single transient blip into a 3am page.
Field practice
Adopt patterns in this order: timeouts, then idempotency, then retries with backoff, then circuit breakers, then bulkheads, then load shedding. Skip ahead and you have complexity without the foundation. Make failure modes visible — emit a metric for every breaker state change, every shed request, every saga compensation. Run a chaos drill at least quarterly; the first one will be humbling. And remember the only reliable system is one that has been broken on purpose enough times that you no longer fear breaking it.
```
Chapter 13 / Defence

Security.

Security is not a feature you add at the end. It is a property of the whole system — authentication tells you who, authorisation tells you what, encryption keeps the wire from gossiping, and good engineering keeps the next attacker honest. The mindset that separates a senior backend engineer from a junior is to assume hostile inputs, untrusted callers, and a future you who has forgotten the threat model. The patterns below are not optional. They are the table stakes for putting anything on the internet.

```

Threat modelling, briefly

Before the controls, the question: what are you defending against? STRIDE — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege — is a useful mnemonic. For each component, ask which of these apply, and what the consequence is. The mistake is asking "is this secure?" — the right question is "secure against what?" A coffee-shop laptop has different threats from a banking core, and the controls should match.

AuthN versus AuthZ

Authentication is "who are you?" — passwords, tokens, certificates, hardware keys. Authorisation is "what may you do?" — roles, permissions, attributes, ownership. They are different problems with different solutions, and confusing them is how privilege escalations happen.

A typical request flow: a gateway authenticates by verifying a token, attaches the claims to the request context, and forwards. Each service authorises by inspecting the claims against its own policy. Authentication centralised at the edge; authorisation distributed to each service. Crucially, services do not re-authenticate — they trust the gateway's signed claims. This is why mTLS between gateway and services matters.

Passwords (if you must)

Avoid storing passwords if you can — delegate to an identity provider via OAuth/OIDC. If you must store them: never plaintext, never reversible encryption, never MD5/SHA-1/SHA-256. Use argon2id (the current OWASP recommendation), or bcrypt as a fallback. Tune the cost parameter so a hash takes ~250ms on your hardware. Salt is included in modern algorithms; you don't need to add your own.

Don't impose dumb password rules. NIST has been clear for years: minimum length 8, check against breach databases (HaveIBeenPwned API), no forced rotation without cause, no silly composition rules. Long passphrases beat complex strings.

OAuth 2.1 & OIDC, what you actually need

OAuth 2 is the protocol for delegated authorisation: a user lets a client app access resources on their behalf without giving up their password. OpenID Connect (OIDC) layers authentication semantics on top — the ID token tells you who the user is.

In 2025, the only OAuth flow you should be implementing for new clients is Authorization Code with PKCE. Implicit flow is deprecated. Resource Owner Password Credentials grant is a security disaster. Client Credentials grant is for machine-to-machine. Everything else is back-compatibility. PKCE protects against authorization-code interception by binding the code exchange to a per-session secret.

Use a battle-tested provider — Auth0, Okta, Keycloak, Cognito, your IdP — rather than writing OAuth yourself. The protocol has more footguns than you have time to encounter.

JWTs: what they're for, what they're not

A JSON Web Token is a signed JSON document. It is excellent for transmitting claims across service boundaries (the gateway signs; downstream services verify with the public key) and terrible as a session store.

The classic JWT pitfalls.

alg=none: some libraries accept an "unsigned" JWT if the token says alg=none. Reject explicitly. Pin the algorithm on the verification side.

Algorithm confusion: a library that accepts both HMAC and RSA can be tricked into verifying an RSA token using the public key as an HMAC secret. Pin the algorithm.

Long expiration: a JWT cannot be revoked. If your access token lives 24 hours, a stolen token is good for 24 hours. Use short access tokens (5–15 min) and refresh tokens stored securely (httpOnly cookies).

Sensitive data in the payload: JWTs are signed, not encrypted. Anyone can decode them. Don't put PII, secrets, or anything you wouldn't print on a billboard.

Logout doesn't log out: revoking a JWT is hard. Keep a server-side revocation list, or use opaque tokens with a real session store. For most apps, "stateful sessions in Redis behind a cookie" is simpler and more secure than JWT-everywhere.
```

```
XSS & CSRF

Cross-site scripting (XSS) is the SQL injection of the browser: attacker-controlled content gets executed as code. Modern frameworks (React, Vue, Angular, Lit) escape by default — XSS in 2025 mostly happens via dangerouslySetInnerHTML, untrusted href values, or rendering Markdown without sanitisation. Use DOMPurify if you must render HTML you didn't write.

Cross-site request forgery (CSRF) tricks a logged-in user's browser into firing a state-changing request to your site. The modern mitigation is SameSite=Lax (or Strict) cookies, which most browsers default to. For double belt-and-braces, add anti-CSRF tokens on sensitive endpoints. APIs that use bearer tokens (not cookies) are immune by construction.

Secrets management

Secrets are not configuration. .env files committed to git, AWS keys in your CI logs, database passwords hardcoded in application.yml — these are how breaches start. Use a real secrets manager: AWS Secrets Manager, HashiCorp Vault, Google Secret Manager, Doppler. Rotate regularly. Audit access. Never log secret values; configure your logging library to redact known sensitive keys.

For service-to-service authentication, use workload identities (AWS IAM roles, Kubernetes service accounts, SPIFFE/SPIRE) rather than long-lived API keys. Short-lived, automatically rotated, attached to the workload — not a string a human ever sees.

TLS everywhere & mTLS for internal calls

TLS in transit is non-negotiable for public traffic. In 2025, TLS 1.3 with strong cipher suites is the baseline; everything below TLS 1.2 should be off. Internally, mTLS — where both sides present certificates — turns the network into a zero-trust fabric: a compromised pod can't talk to a service it isn't issued a cert for. Service meshes (Istio, Linkerd) make mTLS-by-default operationally tractable.

Rate limiting as a security control

Rate limiting is not just about cost; it's about brute force, credential stuffing, enumeration, and DoS. Limit login attempts per account and per IP and per ASN — attackers have proxy farms. Limit expensive operations (signup, password reset, export) more aggressively. Combine with progressive challenges: CAPTCHA after N failures, MFA after N more, lockout after N more.

Supply chain

Most teams' biggest security exposure is in code they didn't write. Generate an SBOM (CycloneDX, SPDX), run continuous CVE scanning (Trivy, Snyk, Dependabot), pin versions, sign artefacts (Sigstore, Cosign), and treat your CI as the production system it actually is. SolarWinds, Log4Shell, xz-utils — the supply chain is the contested ground of the decade.

Warning
Do not invent crypto. Do not modify crypto. Do not turn off certificate validation "just for testing" and forget. Do not roll your own auth. Each of these is a CVE waiting to be issued in your name.
Field practice
Build the security baseline into the platform, not into every service: TLS terminated at the gateway, mTLS for internal, secrets via the manager, auth claims in a verified header, OWASP linting in CI, container scanning, IaC scanning. Threat model new features at design review, not pre-launch. Log security-relevant events (auth, privilege change, data export) and alert on the anomalies. And learn to write the postmortem before the breach: what data could leave the system, by what path, and what would stop it. The answer "nothing" is always wrong, and finding the real answer is the work.
```

Chapter 14 / Eyes

Observability & SLOs.

Monitoring is what you set up when you know what to watch for. Observability is what you need when you don't — when the bug is something nobody predicted, the failure mode is novel, and the only way to find the cause is to ask questions the system can answer in retrospect. Building backend systems without observability is performing surgery in the dark. The instruments are well understood and inexpensive; the question is whether you invest in them before the outage or after.

```

The three pillars (plus one)

Logs are discrete events with rich context. A request, an error, a state transition.

Metrics are numeric measurements aggregated over time. Request rate, error count, latency histogram.

Traces follow one request across multiple services. The end-to-end story of one user click.

Profiles (the often-forgotten fourth) show where CPU time and memory are spent inside a process. Continuous profiling (Pyroscope, Parca, async-profiler) has become cheap enough to run in production.

Each tells you something different. Logs answer "what happened in this case?", metrics answer "how is the system behaving in aggregate?", traces answer "where did this request spend its time?", and profiles answer "what was the CPU doing while it spent that time?". A real observability stack covers all four, with shared identifiers (request ID, trace ID) letting you pivot between them.

Structured logging

Unstructured logs ("User 123 failed login at 14:23:01") are write-only. Structured logs — JSON, with named fields — are queryable. Every modern logger (zap, slog, logback, structlog, pino) emits structured by default; turn it on.
```

“level”:“warn”,

Three habits separate professional logging from amateur.

Stable event names. msg: “auth.failed” is queryable; msg: “User ‘alice’ tried to log in but the password was wrong (3rd time today)” is prose. Put the variability in fields, not in the message.

Propagate context. Request ID and trace ID on every log line in a request. User ID, tenant ID, version. The cost is small; the payoff during an incident is enormous.

Log levels with meaning. ERROR means a human needs to look. WARN means it’s odd. INFO means routine. DEBUG means temporary. If half your ERRORs are noise, on-call starts ignoring all of them. Tune them like you tune alerts.

```

Metrics: the four types

Prometheus codified four metric types now standard everywhere.

Counter — monotonically increasing. http_requests_total, orders_created_total. Compute rates in the query layer (rate(...)).

Gauge — a value that goes up and down. queue_depth, connection_pool_active, memory_used_bytes.

Histogram — pre-bucketed observations, suitable for percentiles. Latency goes here. Aggregation across instances works correctly (sum the bucket counts).

Summary — client-side percentile computation. Cheaper but cannot aggregate meaningfully across instances. Use histograms unless you have a specific reason.

The cardinal sin is high-cardinality labels. Never put a user ID, request ID, session ID, or full URL into a metric label — every unique value becomes a new time series and your TSDB falls over. Labels are for grouping (route, status, region, environment); identifiers belong in logs and traces.

The RED and USE methods

For services: RED — Rate, Errors, Duration. Three dashboards per service: how many requests per second, what fraction error, and the latency distribution. If you have these three, you can answer most "is the service healthy?" questions in seconds.

For resources (CPUs, disks, queues): USE — Utilisation, Saturation, Errors. How busy is it, how much is queued waiting, how many errors. A CPU at 60% utilisation with no run-queue saturation is fine; at 60% with constant run-queue depth is overloaded.

Together, RED on the request path and USE on the resources beneath it cover what you need for the typical service.

Traces

A trace is a tree of spans, each representing a unit of work — an HTTP call, a DB query, a cache lookup. The root is the user-facing request; children are downstream calls. Each span has a duration, a parent, and attributes. Visualised as a flame graph, the slowness of a request becomes obvious: this trace shows that 800ms of a 1.1s request was a single Postgres query in a loop.

OpenTelemetry has won the standards war for trace propagation and SDKs. Whatever backend you choose (Jaeger, Tempo, Honeycomb, Datadog), use OTel for instrumentation so you can switch backends without re-instrumenting.

Sample sensibly. Full tracing of every request is expensive at scale. Tail sampling (keep all error traces and slow traces, sample fast successful traces at 1–10%) retains the diagnostic value while controlling cost.

Cardinality vs. utility

Logs are high-cardinality and slow to query at scale; metrics are low-cardinality and fast; traces are mid-cardinality and per-request. A well-built stack:

• Metrics for dashboards, alerting, and capacity (aggregate behaviour).
• Traces for diagnosing slow individual requests (per-request behaviour).
• Logs for the details when a trace span is interesting (contextual behaviour).
• Profiles for "why is this CPU at 80%" questions.

Each layer should link to the next: a metric spike on the dashboard links to traces in that time window; a slow span links to its log lines; a log line links to its profile. This is the "navigate the elephant" pattern that mature teams adopt.

SLI, SLO, SLA — the discipline

A Service Level Indicator is a measurable property of the service. "Fraction of requests in the last 5 min that returned 2xx in under 300ms" is an SLI.

A Service Level Objective is a target for an SLI. "99.9% of requests return 2xx under 300ms over a rolling 28 days" is an SLO. Internal commitment, derived from what users actually need.

A Service Level Agreement is the contract with customers, with money attached. Usually looser than the SLO — your customers see 99.9%, you target 99.95%.

The breakthrough is the error budget: 99.9% SLO means 0.1% of requests may fail per month — roughly 43 minutes of total downtime. If you burn through that budget, slow releases and invest in reliability. If you're well under, you can ship faster. Reliability becomes a numeric tradeoff, not a values argument.

Alerting that doesn't ruin lives

Bad alerting is worse than no alerting. Three principles.

Alert on symptoms, not causes. Don't alert on "CPU is high" — that's diagnosis. Alert on "the SLO is being burned faster than budgeted" — that's the symptom users feel. High CPU on its own may be fine; SLO burn never is.

Multi-window burn rate alerts. The Google SRE workbook gives the formula: alert when the burn rate over the last 1 hour AND the last 5 minutes exceeds a threshold. This catches both fast outages and slow degradations while ignoring single spikes.

Every alert links to a runbook. Page text says "what does this mean", "what do I check first", "how do I mitigate". An alert at 3am with no runbook is hazing.

Audit your alerts quarterly. Anything that fired without action being needed is noise; mute, tune, or delete. Alert fatigue is the leading cause of missed real incidents.

Note
Averages lie. A service with mean latency 50ms and p99 latency 2 seconds is not "fine on average" — 1 in 100 users is having a terrible time. Always look at percentiles, plot the whole histogram, and pay attention to p99 and p99.9. We'll spend more time on this in the next chapter.
Field practice
Build the observability layer before you need it; you cannot debug an outage with metrics you didn't capture. Instrument every external boundary with RED, every queue and pool with USE, every important business event with a structured log line. Propagate trace and request IDs end-to-end so a single ID joins logs, metrics, and traces. Pick an SLO that reflects user pain (not 100%) and let the error budget drive priorities. Treat alerts as a backlog — every false page is a bug to fix, not a fact to live with. And the night you can answer "why was the p99 high at 14:02 yesterday?" in five minutes is the night you know the stack is finally working.
```

Chapter 15 / Speed

Performance engineering.

Performance is what you measure and what you can change about it. Most of what passes for performance engineering is folklore — "use this framework, it's faster" — repeated by people who have never run a benchmark. The discipline begins by defining what you are trying to make fast, measuring it before you change anything, identifying the bottleneck, changing one thing, and measuring again. Everything else is decoration. Senior engineers know which numbers matter, which lie, and where in the stack speed actually lives.

```

Latency vs. throughput

Latency is how long one request takes. Throughput is how many you can handle per second. They are related but not the same; optimising one often costs the other. A wider parallelism window raises throughput by keeping more in flight, at the cost of per-request latency (queueing time grows). Aggressive batching raises throughput by amortising overhead but hurts latency for the request that has to wait for the batch to fill. Caching helps both. Add a layer of indirection and you usually hurt both.

The first question of any optimisation: which are we trying to improve? An offline pipeline cares about throughput and the wall-clock for the whole job. An interactive API cares about p99 latency. A trading system cares about p99.999. A daily ETL doesn't care about either as long as it finishes before the dashboards refresh.

Percentiles, not averages

A mean latency of 50ms tells you almost nothing. If 99 requests took 10ms and one took 4 seconds, the mean is 50ms — and one user is staring at a hung page. Percentiles tell the truth.

Tail latency & the chain rule

A single service's p99 of 200ms is fine. Compose ten services in series, each with p99 of 200ms, and the p99 of the composed call is much worse than 200ms — because the chance that any one of them is having a bad request is ten times higher. Jeff Dean's famous Google paper on tail latency hammers this home: with N parallel calls to a service with p99 200ms, the chance the slowest is above 200ms approaches 1 - 0.99^N very quickly.

Two mitigations.

Hedged requests. Fire the request to a second replica if the first hasn't responded in p95 time; take whichever comes first. Doubles request rate on a fraction of calls; tames the tail. Google's BigTable did this; you can do it in your client.

Tied requests. Send to two replicas; whichever starts work notifies the other to cancel. Cheaper than full hedging.

Little's Law and why your queues are full

For a stable system: L = λ · W — the average number of items in the system equals the arrival rate times the average time spent. If you accept 1000 req/s and each takes 100ms, you have 100 requests in flight at any moment. If your thread pool has 50 threads, requests are queueing for half their lifetime. The fix is not "add threads" — it's to either reduce W (make requests faster) or λ (shed load).

Little's Law is the most useful equation in performance engineering. Memorise it.

Where the time actually goes

Before optimising, find where time is spent. Almost always, it is one of:

1. Database — slow queries, missing indexes, N+1 patterns, connection pool starvation. Run EXPLAIN ANALYZE; enable pg_stat_statements. This is the bottleneck for ~60% of services.
2. Network calls — synchronous calls to downstream services, especially in serial. Parallelise where possible. Each round trip is a millisecond at best.
3. Serialisation — JSON encoding/decoding of large payloads, especially at gateways. Protobuf is 5–10× faster and smaller.
4. GC pauses in managed runtimes — JVM tuning is a discipline of its own, Go has its own quirks, .NET GC has improved enormously. Profile under load before blaming.
5. Logging and instrumentation — synchronous logging on the hot path is a surprisingly common culprit. Make logging async; batch metric exports.
6. The application code — usually last on the list. Algorithmic improvements (the O(n²) loop you accidentally wrote) can help, but architectural changes have bigger wins.

Profiling: see, don't guess

A profiler shows you where CPU time and memory go. Modern profilers are cheap enough to run in production continuously.

CPU profilers: perf on Linux, async-profiler for JVM, pprof for Go, py-spy for Python, the .NET diagnostic suite. All produce flame graphs (Brendan Gregg's invention) — a visual where width is time and stacks are vertical. Wide bars are the bottleneck.

Memory/allocation profilers: same tools usually. Allocation pressure causes GC pauses and cache thrashing; finding the function allocating 60% of objects is often a free win.

Continuous profiling: Pyroscope, Parca, Datadog APM, Grafana Phlare. Run profilers all the time, all in production, and aggregate. You can now answer "what changed between yesterday and today?" — and see a regression as a new flame in the graph.

Benchmarking honestly

Microbenchmarks lie. They lie because of warmup (JIT), they lie because of cache effects, they lie because the compiler optimises away dead code, they lie because the benchmark itself dominates. JMH for Java, Benchstat for Go, pytest-benchmark for Python are the tools that make microbenchmarks roughly honest — they handle warmup, statistical significance, and noise.

For load tests, use the right tool: k6, wrk, vegeta, Locust. Three rules.

Test from a separate machine. Load generators on the same box as the service contend for CPU; the result is fiction.

Use realistic traffic shapes. A flat 1000 req/s is not what production looks like. Use recorded traces or shapes with peaks, dips, and bursts.

Measure the tail, with enough samples. p99 from 100 requests is one number; p99 from a million is meaningful.

Coordinated omission

The subtle benchmark bug: when a load generator's request is delayed because the service is slow, naive measurement records "I sent at T, response at T+200ms — 200ms latency". But the request would have been sent at T-1s if the generator hadn't been blocked; the actual latency including queueing is 1.2s. This is coordinated omission, Gil Tene's term. wrk2, k6, and HdrHistogram-aware tools correct for it. Your homegrown load test does not.

The five most common quick wins

Before deep optimisation, check that you haven't shipped a known regression.

1. An unindexed query in the hot path (Ch. 6).
2. A serial sequence of network calls that could be parallel (Promise.all, WaitGroup, CompletableFuture).
3. JSON parsing of a payload you only needed one field from.
4. Synchronous logging on the hot path.
5. A misconfigured connection pool (Ch. 6).

When not to optimise

Don Knuth's full quote — "We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%" — is more famously truncated than read. The point is not "don't optimise". It is "know which 3% matters and ignore the rest". Profile, measure, then optimise. Don't change two things at once; you'll learn nothing.

Field practice
Treat performance like a feature: there's a budget, a target, a test, and a regression alarm. Pick a p99 latency for the user-facing flow and a CPU budget for the backend; alert when either drifts. Run continuous profiling in production; a 1% CPU regression today is a 10% regression in a quarter. Before optimising, write down the bottleneck hypothesis and the measurement that would confirm it. If you can't, you don't have a problem yet — you have an opinion. And remember: the fastest call is the one you don't make. Caching, batching, and removing serial dependencies usually beat low-level micro-optimisation by an order of magnitude.
```

Chapter 16 / Substrate

Cloud-native & containers.

The shape of the thing you deploy has changed. Where servers used to be cared for like pets — named, fed, upgraded in place — they are now cattle: created and destroyed in seconds, identical, anonymous, replaced rather than fixed. The technology stack that enables this — containers, orchestrators, declarative infrastructure, programmable networking — is what "cloud-native" means in practice. You don't need to be a Kubernetes operator to be a senior backend engineer, but you need to understand the shapes well enough to debug your service when it doesn't start.

```

Containers, really

A container is a process — just a Linux process — with three kernel features applied: namespaces for isolation (PID, network, mount, user, IPC, UTS), cgroups for resource limits (CPU, memory, IO), and a chrooted filesystem image. It is not a lightweight VM; there is no hypervisor, no separate kernel. The host kernel is shared. This makes containers fast to start (milliseconds) and dense (thousands per host), and is also why they don't isolate as strongly as VMs.

Docker popularised the packaging format. The image is a stack of layers — each line in a Dockerfile creates one — and layers are content-addressed and reusable across images. This is why image pulls are fast: you mostly already have the base layers.

Building images that don't embarrass you

Three habits separate competent images from amateur.

Multi-stage builds. Compile in a fat image with the SDK; copy only the binary into a slim runtime image. A Go binary in scratch is 15MB; in golang:1.22 the same binary is 800MB. 

# Stage 1: build
```

FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# Stage 2: runtime — tiny, no shell, no package manager
FROM gcr.io/distroless/static-debian12
COPY –from=build /app /app
USER nonroot:nonroot
ENTRYPOINT [”/app”]

Pin everything. FROM node:latest means a different image every week and silent breakage in CI. FROM node:20.11.1-alpine means reproducible builds. Use digest pins (node@sha256:…) for the strictest reproducibility.

Run as non-root. Default Dockerfiles run as root; default Kubernetes pods run as root unless you set securityContext. Don’t. Use a non-privileged UID; combine with readOnlyRootFilesystem: true and allowPrivilegeEscalation: false for the secure baseline.

```
Requests and limits, set both

Every container in a Pod should declare CPU and memory requests (what it needs) and limits (what it can't exceed). Requests are what the scheduler uses to place pods; limits are what the kernel enforces.

Pitfalls:

No limits means a misbehaving pod can hog the node and starve neighbours.
CPU limits set too tight cause throttling — your service stalls in bursts. Modern guidance: set CPU request, often no CPU limit.
Memory limits too tight cause OOMKilled — the kernel kills your pod with no chance to clean up.
JVM unaware of cgroup limits historically caused JVMs to think they had the whole node and OOM-kill at the cgroup boundary. Modern JVMs (11+) read cgroups correctly, but always set -XX:MaxRAMPercentage explicitly.

Health checks: liveness vs readiness

Kubernetes asks each container two questions on a schedule.

Liveness: "are you alive?" — if no, kill and restart the pod. Use a lightweight check that fails only on deadlocks/wedged state.

Readiness: "should you receive traffic?" — if no, remove from Service endpoints but don't restart. Use a richer check that returns false if downstreams are broken or warmup isn't complete.

Conflating these is a classic outage maker: a too-aggressive liveness probe restarts pods during a downstream blip, removing capacity right when you need it. Liveness should fail only when restart will help; readiness should fail when traffic will fail anyway.

Service mesh

A service mesh injects a sidecar proxy (Envoy, Linkerd-proxy) next to every pod. The proxy handles mTLS, retries, traffic splitting, observability, and routing. Istio and Linkerd are the mainstream choices.

The honest take: a service mesh is powerful and usually overkill. The features it offers can be acquired piecemeal — gateways for traffic, libraries for retries, observability via OpenTelemetry. Adopt a mesh when you have many services in many languages and need mTLS and traffic policy uniformly; resist it when you have five Go services and a small team. The mesh is a system with its own outages.

Infrastructure as code

Click-ops — making changes in the cloud console — does not scale and does not audit. Everything that exists in your cloud should exist in code, version controlled, reviewed.

Terraform remains the lingua franca; OpenTofu is its open-source fork. AWS CDK and Pulumi let you write in real languages; their abstractions are great for application teams. CloudFormation if you're AWS-only. The choice matters less than the discipline: state in a remote backend, change via pull request, automated plan-and-apply.

For Kubernetes-resident config, GitOps (ArgoCD, Flux) is the modern shape: a git repo is the source of truth, and a controller in the cluster reconciles. We'll revisit in Ch. 17.

Multi-region, briefly

Going multi-region is not a flag; it is a project. The complications cascade.

Data: can your database span regions? Aurora Global, Spanner, CockroachDB can. Postgres replication can be configured to. Each comes with consistency tradeoffs.
Routing: latency-based DNS (Route 53), GeoDNS, or anycast (Cloudflare).
State: sticky sessions, distributed caches with appropriate locality, and the answer to "what is the source of truth when the regions disagree?"
Cost: cross-region data transfer is the silent killer. Watch your bills.

Most companies don't need multi-region; they think they need disaster recovery. A second region warm-standby is usually enough. Active-active is for the few who genuinely operate at multiple-region scale.

FinOps awareness

Cloud bills surprise teams that don't watch them. The pathological patterns: a cron that forgets to delete its scratch S3 bucket, an unused dev environment running at production size, cross-AZ traffic that nobody noticed, log volumes growing 30% a month, a misconfigured DynamoDB on-demand at 10× provisioned cost. Tag every resource, attribute every dollar to a service or team, and review costs monthly. The first time you find a $30k/month line item from a single zombie service is also the first time you understand FinOps.

Note
You don't have to use Kubernetes. ECS Fargate, Cloud Run, Fly, Render, Railway, plain Nomad, even good old VMs with autoscaling — all are reasonable. Kubernetes is appropriate when your scale and team size justify the operational tax. Below that line, you'll spend more time on YAML than on product.
Field practice
Build images that are small, pinned, and non-root. Set requests and limits on every container; distinguish liveness from readiness; expose /healthz and /ready endpoints with care. Keep secrets out of ConfigMaps and out of git; use the cloud's identity for workload auth. Adopt a mesh only when you can't get away with libraries. Tag everything; bill it back to a team. And the most important rule: whatever platform you build on, automate it from day one. Manual cloud changes are how you ship the outage and the audit failure together.
```

Chapter 17 / Cadence

Delivery & operations.

Shipping software is the easy part; shipping it safely, repeatedly, and reversibly is the hard part. A junior engineer thinks the deploy is a one-shot event; a senior engineer treats it as an experiment with a control group, an observation window, and a rollback lever. The difference between the team that releases hourly without incidents and the team that does a quarterly Big Bang Friday deploy is not talent — it is the discipline of delivery and operations, codified into the pipeline.

```

Trunk-based development

Long-lived feature branches are how integration becomes a separate, painful event. Trunk-based development inverts it: everyone commits to main multiple times a day, behind feature flags, with a green build at every commit. Branches live hours, not weeks. The merge conflict you didn't have, the integration test you didn't break, the release you didn't have to coordinate — these are the dividends.

The technique that makes it possible is the feature flag: code paths that exist in production but are conditionally executed. Half-built features can be merged behind a disabled flag, exercised by a few internal users when partially enabled, and gradually ramped to the whole user base. LaunchDarkly, Unleash, Flagsmith, ConfigCat — or your own simple flag service backed by a config repo.

The pipeline shape

A boring, correct CI/CD pipeline looks the same everywhere:

1. Lint & format — static analysis, style checks. Fast feedback.
2. Unit tests — function/class level, in milliseconds total.
3. Integration tests — with real databases, real brokers, via Testcontainers.
4. Build artefact — container image, binary, or package. Signed.
5. Security scans — dependency CVEs, container image scanning, IaC linting.
6. Deploy to staging — same shape as prod, smaller scale.
7. Smoke tests — handful of end-to-end checks against staging.
8. Deploy to production — progressive rollout (next section).
9. Post-deploy verification — synthetic monitors, SLO checks.

Two rules. Anyone can ship, but only the pipeline ships. No manual scp. No "just this once". The pipeline is the only path to production. And the pipeline runs on every commit, not just on the ones intended to ship. Otherwise you discover breakage at deploy time, which is the worst time.

The testing pyramid (with caveats)

Mike Cohn's pyramid — many unit tests, fewer integration tests, even fewer end-to-end — is still broadly right, with modern caveats. Unit tests are cheap and fast; end-to-end tests are slow and flaky. Most of your assurance should come from the bottom.

The modern adjustment is the middle: integration tests with real dependencies via Testcontainers (a real Postgres, a real Redis, in a container, started per test class) are dramatically more valuable than mocked unit tests, and only modestly slower. The argument "but tests should be fast" has lost to "tests should catch the bugs". A 10-minute integration suite that prevents a Friday outage beats a 30-second mock-heavy suite that doesn't.

Contract tests (Pact, Spring Cloud Contract) catch the API mismatch between services without a full end-to-end deployment. Producer publishes a contract; consumer tests against it; both fail fast in their own pipelines if either drifts.

Progressive delivery

A big-bang deploy — replace all instances at once with the new version — is how you turn a bug into an outage. Real deployment is progressive.

Rolling deploy. Replace pods one at a time. The default in Kubernetes Deployments. Tolerable for small changes; not protective against bad code.

Blue-green. Two full environments; flip traffic atomically from blue (old) to green (new). Instant rollback by flipping back. Expensive (2x capacity during transition); classic for stateful or finicky upgrades.

Canary. Route a small percentage (1%, 5%, 10%, …) to the new version; observe error rates and latency; promote or roll back. Argo Rollouts, Flagger, your service mesh, or your gateway can do this. This is the modern default for risk-bearing changes.

Shadow. Send copies of production traffic to the new version without returning its responses. Great for testing read-heavy systems under realistic load before flipping over.

Decouple deploy from release

A subtle but powerful idea: shipping code (deploy) is not the same as turning on a feature (release). With feature flags, you can deploy code on Tuesday and release the feature on Friday after gradual ramping. If the feature breaks, you flip the flag — no rollback, no panic. This is how teams ship 50 times a day without 50 outages a day.

GitOps

The CI/CD model "build artefact and have a script push it" runs from the outside. GitOps inverts: the cluster has a controller that watches a git repo and reconciles. To deploy, you commit a change to the manifest repo (typically a bump of the image tag); the controller notices and applies. ArgoCD and Flux are the tools.

The wins: the cluster state is in git (auditable, reviewable, revertable), no credentials flow from CI to clusters, and "what is running where?" is answered by reading the repo, not by querying production. The cost: a learning curve, and the discipline to put everything — config, secrets references, ingress rules — through pull request.

Database migrations

Code deploys are reversible in seconds; database migrations are not. The senior habit: expand-migrate-contract (introduced in Ch. 6). Schema changes are backwards compatible. Code reads from both the old and new column for a release. Once everything is migrated, code stops reading the old column; only then can it be dropped.

Treat migrations as their own deployable artefact. Run them through a tool (Flyway, Liquibase, Atlas, Goose, Alembic) with a versioned history. Never edit a migration that has shipped; add a new one. And every migration should be reviewed for what it does to a running system — does ALTER TABLE take an exclusive lock? Will it block writes for an hour on a 2TB table?

Incident response

Outages are inevitable. The variable is how you handle them.

The Incident Commander pattern (from FEMA's ICS, adopted by Google SRE): during an incident one person — not the most senior engineer, the one chosen for it — coordinates. They are not debugging. They are running the meeting, assigning roles (subject-matter experts on technical work, a communicator on customer comms, a scribe keeping the timeline), making decisions, and protecting the responders from the chaos of managers asking for updates.

Mitigation before diagnosis. The first goal is to stop the bleeding — roll back, flip the flag, scale up, route around. Find the cause later. A team that diagnoses for an hour before mitigating has prolonged the outage by an hour.

Blameless postmortems. After the incident, write up the timeline, the contributing factors, what worked, what didn't, and the action items. Crucially, no person is the cause. "Alice pushed a bad config" is not a finding; "the config push had no automated validation and no canary stage" is. The goal is to make the next outage less likely, not to find someone to blame.

On-call, sustainably

On-call is part of senior backend work. A good on-call rotation has: enough engineers that it's roughly one week in six or longer; a clear handover; a runbook for every alert; and compensation or time off in recognition. A bad rotation burns engineers out and ends careers.

The single greatest improvement most teams can make to on-call quality is to fix the noise: every false page is a bug. Track them, triage them, fix them. An on-call where 80% of pages are real and actionable is a different job from one where 80% are noise.

The operational maturity ladder

A rough self-assessment.

Level 1 — Manual: deploys via SSH, secrets in env files, alerts in inboxes, no postmortems.
Level 2 — Scripted: CI runs tests, deploys via script, basic dashboards, ad-hoc on-call.
Level 3 — Automated: pipeline-only deploys, IaC, SLOs defined, regular postmortems.
Level 4 — Progressive: canary deploys, feature flags everywhere, error budget driving priorities, chaos engineering.
Level 5 — Self-healing: auto-rollback on SLO burn, auto-scaling on multiple signals, predictive capacity planning, near-zero-touch operations.

Most teams live at 2 or 3 and aspire to 4. There is no shame in this. The goal is to move one rung at a time, not to skip to the top.

Field practice
Make deploys boring. The first time you deploy a change should not be the first time the pipeline has run it; the tenth time should feel exactly like the first. Decouple deploy from release with flags; canary everything that touches the request path; rehearse rollbacks as part of every change. Run incident drills before you need them — the team that has practiced is calm; the team that hasn't is improvising. Write postmortems for near-misses, not just outages. And the central truth: the systems that ship safely many times a day are not the most carefully run — they are the most automatically run. Humans get tired; pipelines do not.
```

Chapter 18 / Practice

Capstones & references.

Knowing the names of patterns is not the same as having shipped them. The four capstone projects below are designed to be built end-to-end — code, infrastructure, observability, a runbook, a chaos test. Each forces you to confront a different cluster of problems from this manual in production conditions. They escalate in difficulty: by the time you finish the fourth, you will have practised every chapter against a real adversary, which is the only credential that matters.

```

Capstone 1 — A URL shortener that doesn't lie

The classic interview problem, taken seriously. Build a service at POST /shorten that takes a URL and returns a short ID; GET /:id redirects. Targets:

• 10,000 req/s on the redirect path with p99 < 20ms.
• Postgres for persistence, Redis as a read-through cache.
• Idempotent shortening — the same long URL by the same user returns the same short ID (idempotency key per Ch. 5).
• Cursor-paginated listing of a user's links (Ch. 5).
• RED metrics on every endpoint, distributed traces with OTel (Ch. 14).
• Containerised, deployed via pipeline, with a canary stage (Ch. 16, 17).
• A chaos test that kills the Redis pod under load and verifies the system stays up by degrading to Postgres (Ch. 12).

What you will learn: how to wire the whole stack together, how the cache layer changes the latency story, where the bottleneck actually is when you load test it (almost certainly the database).

Capstone 2 — A rate-limited API gateway

Build a gateway in front of two backend services. Requirements:

• Auth via JWT, verified against a JWKS endpoint (Ch. 13).
• Sliding-window rate limit per API key, backed by Redis (Ch. 5).
• Circuit breaker per upstream with exponential backoff (Ch. 12).
• Timeout cascade — a 5s end-to-end budget, properly subdivided.
• Structured request logs with correlation IDs that propagate to upstreams (Ch. 14).
• Hot config reload — change rate limits without restarting.
• Load test using k6 with a realistic traffic shape; verify the rate limiter doesn't drop legitimate traffic (Ch. 15).

What you will learn: composition of reliability patterns, the surprising amount of state a "stateless" gateway accumulates, the precise pain of getting timeouts right.

Capstone 3 — A multi-region pub/sub job system

The intermediate distributed systems project. A user submits a job (image transcode, report generation); the system processes it durably and notifies the user when done.

• Kafka as the log of jobs, partitioned by user ID (Ch. 10).
• At-least-once consumption with idempotent workers — a duplicate message must not produce two outputs (Ch. 8).
• Outbox pattern between Postgres and Kafka (Ch. 10).
• A DLQ with an admin tool to inspect and replay (Ch. 10).
• A saga orchestrating the steps (image fetch → transcode → upload → notify) with compensations (Ch. 12).
• A second region in passive standby with cross-region replication; document the RPO/RTO explicitly.
• End-to-end traces showing a job's path across services (Ch. 14).

What you will learn: where exactly-once actually breaks, what a hot partition feels like under load, how much complexity Kafka adds vs a job table, the cost of multi-region the first time you see the bill.

Capstone 4 — A fault-tolerant ledger

The hardest project; do this only after the first three. A double-entry ledger that records money movements and never loses or duplicates a record.

• Strict serialisable on writes — no two transfers can violate invariants under any interleaving (Ch. 8, 11).
• Optimistic concurrency on accounts with retry on conflict (Ch. 8).
• Every transfer is idempotent by client-supplied key (Ch. 5).
• A reconciliation job that, by reading the event log, can reconstruct any account balance from genesis (event sourcing — Ch. 4).
• Postgres serializable isolation, then port it to CockroachDB and compare behaviour under load.
• A Jepsen-style chaos test: partition the cluster while running transfers concurrently; verify no money created or destroyed (Ch. 11).
• Observability: every state change emits an audit event; dashboards show consistency violations as alerts.

What you will learn: that the database isolation level is not optional reading; that "we have transactions" does not mean "we have correctness"; that distributed correctness requires testing, not just thinking. If you can build this and prove it correct under partitions, you are well past senior.

The shape of mastery

A backend system is a small civilisation. It has citizens (services), laws (interfaces), currency (data), borders (security), public works (infrastructure), history (logs), and politics (release coordination). Junior engineers contribute features. Senior engineers shape the civilisation — what is built, what is retired, what is left alone, where the lines are. They have opinions, formed from scars, about which patterns are worth their complexity and which are not. They write things down. They tell the truth in postmortems. They watch the budget — error, money, time — and spend it deliberately.

The chapters of this manual are a map of the territory, not a substitute for walking it. Build the capstones. Run the chaos tests. Stay on call. Write the postmortems. Read the papers. Question every "we've always done it this way". Most of all, write less code than you think you need and remove twice as much as you write. The systems that survive a decade are the simple ones, the ones whose authors had the discipline to say no.

A closing thought
The internet is built on TCP segments sent between machines that may not be working, acknowledged by code that may not be correct, persisting state to disks that may not be honest, observed by humans who may not be awake. That this works at all is a small miracle. That you can build on top of it is the work. Be worthy of the layers beneath you; build carefully for the layers above; and remember that someone, somewhere, will one day debug your code at 3am. Make it kind to them.
```
